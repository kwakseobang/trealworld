아직 없는 코드가 지킬 방향을 테스트로 먼저 세운다

commit 413abc58 files+151 / −2
독자 가정. 헥사고날 아키텍처와 Spring을 잘 아는 독자다. 그 설명은 뺐다. ArchUnit의 동작 방식과, 규칙 5개가 실제로 무엇을 잡고 무엇을 놓치는지에 집중했다. 놓치는 것은 임시 클래스를 넣고 실행해서 확인했다.

1. 먼저 알아야 할 것

이 커밋의 앞

코드는 TrealworldApplication 하나였다 (작업 1). ADR-0002는 패키지 3개와 규칙 5개를 문장으로 정했다. 문장은 아무도 강제하지 않는다. plan의 작업 2는 그 문장을 테스트로 바꾼다. 검증은 두 가지다.

plan의 요구뜻
규칙 1~5가 테스트로 있다규칙 하나를 테스트 하나로 찾을 수 있다
규칙을 일부러 어기면 테스트가 실패한다테스트가 정말로 잡는다

ADR-0002의 규칙 5개

  1. domain은 application과 adapter에 의존하지 않는다.
  2. application은 adapter에 의존하지 않는다.
  3. domain은 Spring에 의존하지 않는다.
  4. adapter끼리는 서로 의존하지 않는다.
  5. 웹 어댑터는 들어오는 포트를 통해서만 application을 쓴다.
ArchUnit은 어떻게 동작하는가

ArchUnit은 소스가 아니고 컴파일된 클래스 파일을 읽는다. 클래스마다 "누구를 참조하는가"를 모은다: 필드의 타입, 메서드의 인자, 애너테이션, 상속. 규칙은 "이 패키지의 클래스는 저 패키지의 클래스를 참조하지 않는다" 같은 문장이다. check()가 규칙을 어긴 참조를 모두 찾아서 AssertionError로 던진다. 보통의 JUnit 테스트 안에서 돈다. Spring은 뜨지 않는다.

문제가 두 개 있다. 첫째, 규칙이 지킬 코드가 아직 없다. 둘째, ADR의 규칙은 "웹 어댑터", "들어오는 포트"라고 말한다. 테스트는 패키지의 이름이 필요하다.

2. 핵심 아이디어

벽을 먼저 세우고, 그 뒤에 방을 채운다. 벽이 정말 막는지는 일부러 부딪쳐서 확인한다.

코드가 없을 때 규칙을 세우면, 뒤에 생기는 모든 코드는 처음부터 규칙 안에서 태어난다. 그러나 지킬 코드가 없는 규칙은 항상 통과한다. 통과가 "규칙이 옳다"인지 "검사한 것이 없다"인지 알 수 없다. 그래서 규칙마다 위반하는 클래스를 임시로 넣었다. 5개가 각각 실패하는 것을 보고, 지웠다. 이 실험은 커밋에 없다. 일지에만 있다.

누가 누구에게 의존할 수 있는가

모든 칸은 임시 클래스를 넣고 테스트를 실행해서 확인했다.

스텝 3 — 클래스 파일을 한 번 읽어 들인다

왜: 규칙 5개가 같은 클래스 집합을 본다. 한 번 읽고 함께 쓴다.

ArchitectureTests.java (이어서)

    private static final JavaClasses classes = new ClassFileImporter()            .withImportOption(ImportOption.Predefined.DO_NOT_INCLUDE_TESTS)            .importPackages("trealworld");

볼 곳:

  • DO_NOT_INCLUDE_TESTS — 테스트 코드는 검사하지 않는다. 테스트는 모든 계층을 건드려도 된다. 이 선택 때문에 위반 실험의 임시 클래스를 src/main에 넣어야 했다.

재료가 준비됐다. 이제 규칙이다. 먼저 모양이 같은 3개다.

스텝 4 — 안쪽은 바깥쪽을 모른다 (규칙 1, 2, 3)

왜: 세 규칙은 같은 문장이다. "A의 클래스는 B의 클래스에 의존하지 않는다." A와 B만 다르다.

    @Test    void rule1_domain_does_not_depend_on_application_or_adapter() {        noClasses().that().resideInAPackage(DOMAIN)                .should().dependOnClassesThat().resideInAnyPackage(APPLICATION, ADAPTER)                .as("ADR-0002 규칙 1: domain은 application과 adapter에 의존하지 않는다")                .allowEmptyShould(true)                .check(classes);    }     @Test    void rule2_application_does_not_depend_on_adapter() {        noClasses().that().resideInAPackage(APPLICATION)                .should().dependOnClassesThat().resideInAPackage(ADAPTER)                .as("ADR-0002 규칙 2: application은 adapter에 의존하지 않는다")                .allowEmptyShould(true)                .check(classes);    }     @Test    void rule3_domain_does_not_depend_on_spring() {        noClasses().that().resideInAPackage(DOMAIN)                .should().dependOnClassesThat().resideInAPackage("org.springframework..")                .as("ADR-0002 규칙 3: domain은 Spring에 의존하지 않는다")                .allowEmptyShould(true)                .check(classes);    }

볼 곳:

  • 테스트의 이름이 rule1_, rule2_, rule3_으로 시작한다. ADR-0004는 "이름에 ID를 넣는다"고 정했다. ADR-0002의 규칙 번호가 ID다.
  • .as("ADR-0002 규칙 1: …") — 실패했을 때의 메시지다. 실패한 사람은 메시지에서 문서의 위치를 바로 안다.
  • 규칙 3은 규칙 1과 다른 것을 지킨다. 규칙 1은 우리 코드의 안쪽 방향이다. 규칙 3은 프레임워크다. 도메인에 @Component 하나가 붙으면 도메인 테스트에 Spring이 필요해진다.
  • .allowEmptyShould(true) — ArchUnit은 "검사한 클래스가 0개"이면 기본으로 실패한다. 지금은 패키지가 비어 있어서 이 줄로 풀었다. 임시다. 검토 메모 1을 본다.

큰 방향 3개가 막혔다. 남은 2개는 adapter의 안쪽을 본다. 문장의 모양이 다르다.

스텝 5 — 어댑터는 서로 모르고, 웹은 포트만 안다 (규칙 4, 5)

왜: 규칙 1~3은 패키지 3개의 사이를 본다. 규칙 4와 5는 패키지 하나의 안과, 경계의 좁은 문을 본다.

    @Test    void rule4_adapters_do_not_depend_on_each_other() {        slices().matching("trealworld.adapter.(*)..")                .should().notDependOnEachOther()                .as("ADR-0002 규칙 4: adapter끼리는 서로 의존하지 않는다")                .allowEmptyShould(true)                .check(classes);    }     @Test    void rule5_web_adapter_uses_application_only_through_incoming_ports() {        noClasses().that().resideInAPackage(WEB_ADAPTER)                .should().dependOnClassesThat(resideInAPackage(APPLICATION).and(not(resideInAPackage(INCOMING_PORT))))                .as("ADR-0002 규칙 5: 웹 어댑터는 들어오는 포트를 통해서만 application을 쓴다")                .allowEmptyShould(true)                .check(classes);    }

볼 곳:

  • 규칙 4의 (*) — adapter의 바로 아래 패키지 하나가 "조각" 하나다. adapter.web, adapter.persistence, adapter.security가 각각 조각이다. 조각의 이름을 적지 않았다. 새 어댑터가 생기면 자동으로 조각이 된다.
  • 규칙 5의 조건은 "application에 있고, 그리고 application.port.in에 있지 않은 클래스"다. 웹 어댑터에게 application은 문 하나(port.in)만 열려 있다. 나가는 포트(port.out)도 막힌다.

규칙 5개가 모두 테스트가 됐다. 지킬 코드는 작업 3(도메인)부터 생긴다.

5. 검토 메모

"확인"은 임시 클래스를 넣고 테스트를 실행해서 본 것이다. "추정"은 코드를 읽고 판단한 것이다.

  • [확인] 1. 지금의 초록은 오타도 통과시킨다. 검사할 클래스가 0개인데 5개가 통과한다. allowEmptyShould(true) 때문이다. 이 줄이 남아 있으면, 누가 "trealworld.domian.."으로 잘못 써도 규칙은 조용히 통과한다. → 규칙 1, 3은 작업 3에서, 규칙 2, 4, 5는 작업 4에서 이 줄을 지워야 한다. 일지의 "남은 일"에만 적혀 있다. plan에는 없다.
  • [확인] 2. adapter의 바로 아래에 둔 클래스는 규칙 4가 보지 않는다. trealworld.adapter.Direct가 adapter.web과 adapter.persistence를 둘 다 참조해도 통과했다. (*)는 하위 패키지가 있어야 맞는다. → "adapter의 바로 아래에는 클래스를 두지 않는다"는 규칙이 없다.
  • [확인] 3. 영속성 어댑터와 보안 어댑터는 application의 아무 클래스나 쓸 수 있다. adapter.persistence.P가 application.Svc(포트가 아닌 클래스)를 참조해도 통과했다. 규칙 5는 웹만 본다. ADR-0002의 문장이 그렇다. 테스트는 문장을 그대로 옮겼다. 문장을 넓힐지는 사용자가 정한다.
  • [확인] 4. application은 Spring을 쓸 수 있다. @Service를 붙여도 통과했다. ADR-0002의 표는 "application이 의존해도 되는 것: domain"이라고 쓴다. 표와 규칙이 다르다. 유스케이스에 @Service와 @Transactional을 쓸지는 작업 4에서 부딪친다.
  • [확인] 5. domain의 JPA는 통과한다. [추정] 다른 라이브러리도 통과한다. ADR의 표는 "Java, JPA 애너테이션, Lombok만"이다. 규칙 3은 Spring만 막는다. 도메인이 Hibernate나 Jackson의 클래스를 직접 써도 테스트는 잡지 못한다.
  • [추정] 6. 규칙 4는 작업 6의 설계를 미리 정한다. AC-3.5는 "토큰이 유효해도 회원이 없으면 거부한다"다. 보안 어댑터가 회원의 존재를 확인해야 한다. 규칙 4 때문에 보안 어댑터는 영속성 어댑터를 직접 쓸 수 없다. application의 포트를 거쳐야 한다.
  • [확인] 7. 위반 실험의 증거는 저장소에 없다. 임시 클래스는 지웠다. "5개가 각각 실패했다"는 일지의 표로만 남았다. 다시 확인하려면 실험을 다시 해야 한다. 작업 3부터는 실제 코드가 규칙의 대상이 되므로 받아들일 수 있다.
  • [질문] 8. AI가 정한 이름이 승인된 ADR에 들어갔다. application.port.in, adapter.web이다. ADR-0002의 상태 줄에 "수정 (작업 2)"을 남겼다. 바꾸려면 지금이 가장 싸다. 이 이름을 쓰는 코드가 아직 테스트뿐이다.

6. 이해했는지 확인하기

점수를 매기는 시험이 아니다. 아직 이해하지 못한 곳을 찾는 도구다. 권장하는 규칙: 통과하기 전에는 이 변경의 검토를 요청하지 않는다.

  1. 테스트 5개를 쓰고 처음 돌렸을 때 5개가 모두 통과했다. 이 통과는 무엇을 증명하는가?

    패키지에는 package-info.java만 있고, 이 파일은 클래스 파일을 만들지 않는다. 규칙은 검사할 것이 없어서 통과했다. 문법이 맞는다는 것은 컴파일이 증명한다. "위반을 잡는다"는 위반을 넣어야 증명된다. 그래서 plan이 "일부러 어긴다"를 검증으로 요구한다.

    다시 읽기: 핵심 아이디어

  2. 작업 6에서 adapter.security의 필터가 adapter.persistence의 리포지토리 구현을 직접 주입받는다. 어떻게 되는가?

    규칙 4는 adapter의 바로 아래 패키지 하나를 조각 하나로 본다. security와 persistence는 다른 조각이다. 규칙 5는 웹 어댑터와 application의 사이만 보므로 이 경우와 관계가 없다. 보안 어댑터는 application의 포트를 거쳐야 한다.

    다시 읽기: 스텝 5

  3. adapter.persistence의 클래스가 application에 있는 유스케이스의 구현 클래스(포트가 아니다)를 참조한다. 어떻게 되는가?

    규칙 2는 방향이 반대다 (application → adapter를 막는다). 규칙 5는 "웹 어댑터"만 본다. 영속성 어댑터에는 "포트만 쓴다"는 규칙이 없다. 테스트는 ADR-0002의 문장을 그대로 옮겼고, 그 문장이 웹만 말한다.

    다시 읽기: 검토 메모 3

  4. 규칙 5를 "웹 어댑터는 application에 의존하지 않는다"로 잘못 썼다고 하자. 위반 실험에서 위반 클래스(V5: 웹 → 포트가 아닌 클래스)만 넣었다면 실험의 결과는?

    잘못 쓴 규칙도 V5를 잡는다. 위반 실험은 "잡아야 할 것을 잡는가"만 본다. 잘못 쓴 규칙의 문제는 "잡지 말아야 할 것(웹 → 들어오는 포트)도 잡는다"다. 그것은 허용된 의존을 넣어야 보인다. 그래서 실험에 대조군(TmpOk)이 있었다.

    다시 읽기: 의존의 표

  5. 작업 3에서 domain에 클래스가 생겼다. allowEmptyShould(true)는 지우지 않았다. 그 뒤에 누가 상수를 "trealworld.domian.."으로 잘못 고쳤다. 어떻게 되는가?

    패키지의 이름은 문자열이다. 컴파일러는 보지 않는다. ArchUnit의 기본 동작은 b가 맞다. 그러나 allowEmptyShould(true)가 그 안전장치를 껐다. 그래서 이 줄은 임시이고, 패키지에 클래스가 생기는 작업에서 지워야 한다.

    다시 읽기: 검토 메모 1
