# Domain 01. 회원

- 상태: 승인 (2026-11-16). 수정 (2026-11-17): R4의 길이 제한과 포트의 위치를 고쳤다. 수정 (2026-11-17, 작업 4): 비밀번호를 값 객체(`Password`)로 적었다. 수정 (2026-11-17): RFC 2119와 ASD-STE100의 원칙으로 다시 썼다. 뜻이 흐린 문장 1곳은 그때의 코드와 같은 뜻으로 좁혔다 (R3. 일지의 스텝 42). ID는 바꾸지 않았다. 수정 (2026-11-17, 사용자가 결정): R2와 R3에 길이의 상한을 더했다. 승인 (2026-11-17, 스텝 54): AI가 좁힌 곳을 사용자가 AI의 권장대로 받아들였다. 하나씩 보지는 않았다. 목록은 일지의 스텝 54에 있다.
- 범위: [Spec 01](../spec/01-member-signup-login.md)에 필요한 것만 다룬다.

## 이 문서를 읽는 법

굵게 쓴 **반드시 ~해야 한다**(MUST), **절대 ~해서는 안 된다**(MUST NOT), **~하는 것을 권장한다**(SHOULD), **~할 수 있다**(MAY)는 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119)의 뜻으로 쓴다. 표는 [Spec 01](../spec/01-member-signup-login.md#이-문서를-읽는-법)에 있다.

- 이 문서는 "~할 수 있다"를 허용의 뜻으로만 쓴다.
- 굵은 말이 없는 문장은 요구가 아니다. 설명이다.

## 용어

한 개념에는 **반드시** 한 용어만 써**야 한다**. 문서, 대화, 코드에서 같은 말을 쓴다.

| 용어 | 코드 이름 | 뜻 |
|---|---|---|
| 방문자 | — | 로그인하지 않은 사람 |
| 회원 | `Member` | 가입한 사람. 이 도메인의 중심이다 |
| 사용자 이름 | `Username` | 회원이 정한 공개 이름. 회원마다 다르다 |
| 이메일 | `Email` | 회원의 이메일 주소. 회원은 로그인할 때 이메일을 낸다. 회원마다 다르다 |
| 비밀번호 | `Password` | 회원만 아는 원문. 시스템은 비밀번호를 저장하지 않는다 |
| 비밀번호 해시 | `PasswordHash` | 비밀번호에서 만든 값. 이 값에서 비밀번호를 다시 얻지 못한다. 시스템은 이 값만 저장한다 |
| 가입 | `register` | 방문자가 회원이 되는 일 |
| 로그인 | `login` | 회원이 이메일과 비밀번호로 자기를 증명하는 일 |
| 액세스 토큰 | `AccessToken` | 로그인의 증거. 회원은 이후의 요청에 액세스 토큰을 낸다 |

회원과 사용자 이름을 가리킬 때 아래의 말은 **절대** 써**서는 안 된다**.

| 쓰지 않는 말 | 대신 쓰는 말 |
|---|---|
| 유저, 사용자 | 회원 |
| 닉네임 | 사용자 이름 |
| 계정 | (정하지 않았다) |

이 프로젝트의 문서에서 혼자 쓴 "사용자"는 회원이 아니다. 프로젝트를 이끄는 사람이다 (예: "사용자가 승인했다").

## 모델

- **회원**이 유일한 애그리거트다. 회원은 사용자 이름, 이메일, 비밀번호 해시를 가진다.
- **이메일**, **사용자 이름**, **비밀번호 해시**는 값 객체다. 값 객체는 자기의 형식 규칙을 스스로 검사한다.
- **비밀번호**도 값 객체다. 비밀번호는 길이의 규칙(R4)을 스스로 검사한다. 회원은 비밀번호를 가지지 않는다. 비밀번호는 가입과 로그인의 동안에만 있다.
- **액세스 토큰**은 도메인 모델이 아니다. 인증 기술의 산출물이다. 도메인은 "누가 요청했는가"(회원의 식별자)만 안다.

## 규칙

| ID | 수준 | 규칙 | 지키는 곳 |
|---|---|---|---|
| R1 | MUST | 회원은 사용자 이름, 이메일, 비밀번호 해시를 **반드시** 가져**야 한다**. 셋 중 하나라도 없는 회원은 없다. | 회원 |
| R2 | MUST | 이메일은 **반드시** 올바른 형식이**어야 한다**. 이메일은 **반드시** 254자 이하**여야 한다**. 이메일은 **반드시** 소문자로 바꿔서 저장**해야 한다**. | 이메일 |
| R3 | MUST | 사용자 이름은 **반드시** 한 자 이상이**어야 한다**. 사용자 이름은 **반드시** 50자 이하**여야 한다**. 사용자 이름의 앞뒤 공백은 **반드시** 지워**야 한다**. 길이는 공백을 지운 뒤에 센다. | 사용자 이름 |
| R4 | MUST | 비밀번호는 **반드시** 8자 이상이**어야 한다**. 비밀번호는 **반드시** UTF-8로 72바이트 이하**여야 한다**. 문자 종류의 조건은 없다. 한 자는 유니코드의 코드 포인트 하나다. | 비밀번호 (가입이 만든다) |
| R5 | MUST NOT | 비밀번호의 원문을 **절대** 저장**해서는 안 된다**. 회원은 비밀번호 해시만 가진다. | 회원 |
| R6 | MUST NOT | 두 회원의 이메일이 **절대** 같**아서는 안 된다**. | 가입 |
| R7 | MUST NOT | 두 회원의 사용자 이름이 **절대** 같**아서는 안 된다**. | 가입 |
| R8 | MUST | 로그인은 **반드시** 이메일로 회원을 찾**아야 한다**. 로그인은 비밀번호가 그 회원의 비밀번호 해시와 맞는지 **반드시** 확인**해야 한다**. | 로그인 |
| R9 | MUST NOT | 로그인이 실패하면 로그인은 이유(없는 이메일, 틀린 비밀번호)를 **절대** 구분**해서는 안 된다**. | 로그인 |
| R10 | MUST NOT | 조회는 회원에게 다른 회원의 정보를 **절대** 돌려줘**서는 안 된다**. 회원은 자기의 정보만 조회한다. | 조회 |

R6과 R7은 회원 하나가 혼자 지키지 못한다. 다른 회원을 알아야 하기 때문이다. 그래서 가입을 처리하는 곳이 저장소에 묻는다.

R2, R3, R4에서 한 자는 유니코드의 코드 포인트 하나다.

R2의 "254자"는 SMTP 표준(RFC 5321)에서 쓰는 주소의 최대 길이다. R3의 "50자"는 사용자가 정했다. 두 숫자는 DB의 열의 길이에서 나온 것이 아니다. DB의 열의 길이가 이 숫자를 따른다.

R4의 "72바이트"는 도메인에서 나온 숫자가 아니다. 해시 기술(BCrypt)의 제한이다. 기술의 제한이 규칙에 들어온 곳은 여기 하나다. 이유는 [ADR-0003](../adr/0003-authentication.md)에 있다.

## 규칙이 밖에 기대는 것

도메인은 기술을 모른다. 아래의 두 가지는 **반드시** `application`의 나가는 포트**여야 한다**. `domain`에는 인터페이스를 **절대** 두**어서는 안 된다** ([ADR-0002](../adr/0002-hexagonal-architecture.md)).

- 회원을 저장한다. 이메일이나 사용자 이름으로 회원을 찾는다.
- 비밀번호를 비밀번호 해시로 바꾼다. 비밀번호가 비밀번호 해시와 맞는지 확인한다.
