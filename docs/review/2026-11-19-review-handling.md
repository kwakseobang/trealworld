## 반영하지 않은 것 — 동의하지 않는다

| 발견 | 리뷰의 주장 | 동의하지 않는 이유 |
|---|---|---|
| ARCH-05 | 영속성 어댑터가 모든 무결성 오류를 "중복"으로 바꾼다. 제약의 이름으로 필드를 가려야 한다 | 지금의 방식은 결정한 것이다. 어댑터는 어느 제약인지 읽지 않는다. DB마다 다르기 때문이다. 유스케이스가 다시 확인하고, 중복이 아니면 500으로 보낸다. 결과는 맞다. 제안은 제약의 이름을 읽는 DB에 묶인 코드를 더한다. 길이의 초과는 ARCH-01의 수정으로 값 객체가 먼저 막는다. 남는 약점: 예외의 이름(`MemberNotUniqueException`)이 "중복일 수도 있다"는 뜻을 말하지 않는다 |
| ARCH-08 | 필드의 타입이 틀린 400에 `errors.필드`가 없다 | ADR-0005에 "읽지 못하는 본문의 400에는 `errors`가 없다"고 적었다 (DOC11). 필드를 알려면 웹 어댑터가 JSON 라이브러리의 예외의 안을 읽어야 한다. 얻는 것이 작다. 문자열이 아닌 값은 아래의 "결정"의 2번에서 400으로 정했다 |
| ARCH-12 | 보안 어댑터가 401의 본문을 `ProblemDetail`이 아니라 맵으로 만든다 | 본문의 모양은 수용 테스트가 고정한다 (필드, `instance`, 이유마다 같은 본문). 바꿔도 동작이 같다. `ProblemDetail`을 필터에서 직접 직렬화하면 MVC의 설정과 다른 결과가 나올 수 있다. 확인하지 않았다 (추정) |
| SEC4 (로그) | 500의 원인이 로그에 남는다. 원인에 해시가 있으면 로그에 보인다 | ADR-0005의 결정이다: "원인은 로그에만 남긴다". 원인이 없는 로그로는 장애를 찾지 못한다. 테스트의 "해시가 든 예외의 글"은 테스트가 만든 것이다. 실제로 해시를 글에 넣는 코드는 리뷰어도 찾지 못했다. `PasswordHash.toString()`은 가렸다 (ARCH-16) |
| ARCH-03 (case folding) | `Σ`와 `ς`는 대소문자만 다른데 다른 이메일이 된다 | R2의 규칙은 "소문자로 바꾼다"이다. case folding이 아니다. Domain 01에 그 뜻과 이 예를 적었다. case folding으로 바꾸면 저장하는 값이 사용자가 낸 값과 더 달라진다 (`ß` → `ss`) |
| TEST9 | 만료의 수용 테스트가 실제의 시간에 기댄다 | 추정이다. 리뷰어도 실패를 보지 못했다. 여유는 10초다. 테스트는 병렬로 돌지 않는다. 만료의 경계는 고정한 시계의 단위 테스트가 본다 (이번에 더했다) |

## 결정 — 리뷰가 남긴 것

처음에는 이 7행을 "동의한다. 결정이 필요하다"로 남겼다. 사용자가 AI의 권장을 따르기로 했다 (2026-11-19, 일지의 스텝 79). 아래는 AI가 정한 것이다. 사용자가 하나씩 보지는 않았다.

| # | 발견 | 결정 | 이유 | 한 일 |
|---|---|---|---|---|
| 1 | ARCH-09, SEC2 (본문의 상한) | **넣지 않는다.** 받아들인 한계로 적는다 | 상한을 넣으면 새 응답(413)과 필터가 생긴다. 이 슬라이스의 목표(가입, 로그인, 조회)의 밖이다. 보통은 서버의 앞의 프록시가 하는 일이다. 필드의 길이를 먼저 보는 것은 이미 반영했다 | Spec 01의 "받아들인 한계"와 ADR-0005에 적었다. 코드는 그대로다 |
| 2 | ARCH-10 (문자열이 아닌 값) | **받지 않는다.** 숫자와 참거짓을 글자로 바꾸지 않는다. 400이다 | `{"password": 12345678}`로 가입이 됐다 (실제 서버에서 201을 봤다). 클라이언트의 잘못을 조용히 받아들이는 동작이다. 비밀번호에서 특히 놀랍다 | `JsonRequestConfig`를 더했다. 테스트 4개. 고치기 전: 201과 401 |
| 3 | ARCH-10 (모르는 필드) | **무시한다.** 지금의 동작을 유지한다 | 거부하면 클라이언트가 필드를 더할 때마다 깨진다. 모르는 필드가 회원의 값이 되지 않는 것만 지키면 된다 | 테스트 1개: `id`, `passwordHash`, `role`을 보내도 무시한다. 처음부터 통과했다 |
| 4 | SEC8 (로그인의 시도 횟수) | **넣지 않는다.** 받아들인 한계로 적는다 | 리뷰어도 "범위 밖"으로 표시했다. 제한은 저장소(횟수)와 정책(출발지, 시간)이 필요하다. 다음 slice의 일이다 | Spec 01의 "받아들인 한계"에 적었다. "서버를 밖에 열기 전에 정해야 한다"도 적었다 |
| 5 | DOC7 ("비어 있다") | **지금의 동작을 뜻으로 정한다.** 비어 있다 = 필드가 없다, `null`, `""`. 사용자 이름과 이메일은 공백만 있는 값도 거부한다. 비밀번호의 공백은 글자다 | 동작을 바꾸지 않는다. 문서가 동작을 말하게 한다. 비밀번호의 공백을 글자로 보는 것은 R4("문자 종류의 조건은 없다")와 맞다. 그래서 공백만 있는 비밀번호의 로그인은 400이 아니라 401이다 | Spec 01의 "이 문서를 읽는 법"에 적었다. 일지의 스텝 54의 "남긴 것" 1개가 닫혔다 |
| 6 | DOC14 (Plan 01의 키워드) | **Plan 01을 다시 쓰지 않는다.** 다음 plan부터 규칙을 따른다 | Plan 01은 끝났다. 문체의 규칙보다 먼저 썼다. 끝난 문서를 다시 쓰면 기록이 바뀐다 | Plan 01에 "읽는 법" 1줄을 더했다 |
| 7 | TEST7 (다른 경로의 상태, 본문의 대상) | **지금의 동작을 계약으로 정한다.** 없는 경로는 404, 받지 않는 메서드는 405다. 조회는 본문을 읽지 않는다 | 실제 서버에서 봤다. Spring의 기본 동작이고 뜻이 맞다. "200이 아니다"는 500도 통과시킨다 | ADR-0005의 표에 2행을 더했다. 테스트: 404, 405, 본문에 다른 회원의 이메일이 없다, 본문으로 다른 회원을 가리켜도 자기의 정보다, 본문의 토큰은 401이다 |
| 8 | TEST15 (방화벽이 거부한 경로의 `instance`) | **`instance`는 클라이언트가 보낸 경로 그대로다** (`/api/members/me;x=1`) | 실제 서버에서 봤다. ADR-0005의 "오류가 난 요청의 경로"와 맞다. 경로를 고쳐서 돌려주면 클라이언트가 자기의 요청을 찾지 못한다 | ADR-0005에 적었다. 테스트의 단언을 "같다"로 바꿨다 |

발견으로는 3개와 일부 4개다. ARCH-10을 둘로 나눠서 표는 8행이다.

밖에서 보이는 동작이 바뀐 곳은 1개다 (2번): 문자열이 아닌 값은 이제 400이다. 맨 위의 "동작이 바뀐 곳"의 6번째다.

## 리뷰에 없던 것

- 리뷰어는 gradle을 실행하지 않았다. "확인"은 코드를 읽은 것이다. 실행의 확인은 처리하는 쪽이 했다.
- 결정을 반영하면서 Spec 01, ADR-0005, Plan 01을 한 번 더 고쳤다.
- 리뷰를 반영하면서 승인된 문서 6개를 고쳤다 (Spec 01, Domain 01, ADR-0002, 0003, 0004, 0005). 문장은 AI가 썼다. 상태의 줄에 적었다.
