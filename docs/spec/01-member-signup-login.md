# Spec 01. 회원 가입 · 로그인 · 내 정보 조회

- 상태: 승인 (2026-11-16). 수정 (2026-11-17): 검토에서 찾은 빈틈을 닫았다. AC-1.4, 1.7, 2.4를 고치고 AC-1.8, 2.5, 3.5를 더했다. 수정 (2026-11-17): RFC 2119와 ASD-STE100의 원칙으로 다시 썼다. 뜻이 흐린 문장 3곳은 그때의 코드와 같은 뜻으로 좁혔다 (AC-2.3, "거부한다", 가정 3. 일지의 스텝 42). ID는 바꾸지 않았다. 수정 (2026-11-17, 사용자가 결정): AC-1.9를 더했다. 사용자 이름과 이메일의 길이의 상한이다. 승인 (2026-11-17, 스텝 54): AI가 좁힌 곳을 사용자가 AI의 권장대로 받아들였다. 하나씩 보지는 않았다. 목록은 일지의 스텝 54에 있다.
- 슬라이스: 가입 → 로그인 → 회원 정보 조회 (킥오프 6.8)
- 용어: [도메인 모델](../domain/01-member.md)을 따른다.

이 문서는 **무엇을** 만드는지만 말한다. API의 모양과 기술은 [ADR](../adr/)에 있다.

## 이 문서를 읽는 법

굵게 쓴 아래의 말은 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119)의 뜻으로 쓴다.

| 말 | RFC 2119 | 뜻 |
|---|---|---|
| **반드시 ~해야 한다** | MUST | 예외가 없는 요구다. |
| **절대 ~해서는 안 된다** | MUST NOT | 예외가 없는 금지다. |
| **~하는 것을 권장한다** | SHOULD | 이유가 있으면 따르지 않아도 된다. 그 이유를 적는다. |
| **~할 수 있다** | MAY | 허용이다. 해도 되고 하지 않아도 된다. |

- 이 문서는 "~할 수 있다"를 허용의 뜻으로만 쓴다. 능력이나 가능성을 말할 때는 다른 말을 쓴다.
- 굵은 말이 없는 문장은 요구가 아니다. 설명이다.
- "시스템"은 이 슬라이스가 만드는 백엔드다.
- "결과"는 시스템이 요청에 돌려주는 내용이다. 성공의 결과와 거부의 결과가 모두 들어간다.
- "거부한다"는 두 가지를 뜻한다. 시스템은 요청한 일을 하지 않는다. 시스템은 거부한 것을 결과로 알려준다.

## 목표 1. 방문자가 회원으로 가입한다

방문자가 사용자 이름, 이메일, 비밀번호를 낸다. 방문자가 회원이 된다.

| ID | 수준 | 수용 기준 |
|---|---|---|
| AC-1.1 | MUST | 값이 모두 올바르면 시스템은 **반드시** 회원을 만들**어야 한다**. 시스템은 결과로 사용자 이름과 이메일을 **반드시** 돌려줘**야 한다**. |
| AC-1.2 | MUST | 사용자 이름, 이메일, 비밀번호 중 하나라도 비어 있으면 시스템은 **반드시** 가입을 거부**해야 한다**. 시스템은 어느 값이 문제인지 **반드시** 알려줘**야 한다**. |
| AC-1.3 | MUST | 이메일의 형식이 틀리면 시스템은 **반드시** 가입을 거부**해야 한다**. |
| AC-1.4 | MUST | 비밀번호가 8자보다 짧으면 시스템은 **반드시** 가입을 거부**해야 한다**. 비밀번호가 UTF-8로 72바이트보다 길면 시스템은 **반드시** 가입을 거부**해야 한다**. |
| AC-1.5 | MUST | 이메일이 이미 있으면 시스템은 **반드시** 가입을 거부**해야 한다**. |
| AC-1.6 | MUST | 사용자 이름이 이미 있으면 시스템은 **반드시** 가입을 거부**해야 한다**. |
| AC-1.7 | MUST NOT | 시스템은 어떤 결과에도 비밀번호와 비밀번호 해시를 **절대** 넣어**서는 안 된다**. |
| AC-1.8 | MUST | 시스템은 대소문자만 다른 이메일을 **반드시** 이미 있는 이메일로 봐**야 한다**. |
| AC-1.9 | MUST | 사용자 이름이 50자보다 길면 시스템은 **반드시** 가입을 거부**해야 한다**. 이메일이 254자보다 길면 시스템은 **반드시** 가입을 거부**해야 한다**. 두 경우에 시스템은 어느 값이 문제인지 **반드시** 알려줘**야 한다**. |

## 목표 2. 회원이 로그인한다

회원이 이메일과 비밀번호를 낸다. 회원이 액세스 토큰을 받는다.

| ID | 수준 | 수용 기준 |
|---|---|---|
| AC-2.1 | MUST | 이메일과 비밀번호가 맞으면 시스템은 **반드시** 액세스 토큰을 돌려줘**야 한다**. |
| AC-2.2 | MUST | 비밀번호가 틀리면 시스템은 **반드시** 로그인을 거부**해야 한다**. |
| AC-2.3 | MUST | 이메일이 없으면 시스템은 **반드시** 로그인을 거부**해야 한다**. 이 결과의 내용은 AC-2.2의 결과의 내용과 **반드시** 같**아야 한다**. 응답 시간은 이 기준의 대상이 아니다 ("받아들인 한계"를 본다). |
| AC-2.4 | MUST | 이메일이나 비밀번호가 비어 있으면 시스템은 **반드시** 로그인을 거부**해야 한다**. 이메일의 형식이 틀리면 시스템은 **반드시** 로그인을 거부**해야 한다**. 두 경우에 시스템은 값의 오류로 **반드시** 알려줘**야 한다**. 이 결과는 AC-2.2의 결과와 **반드시** 달라**야 한다**. |
| AC-2.5 | MUST | 이메일의 대소문자가 가입할 때와 달라도 시스템은 **반드시** 로그인을 받아들여**야 한다**. |

## 목표 3. 회원이 자기 정보를 조회한다

로그인한 회원이 액세스 토큰을 낸다. 회원이 자기의 정보를 받는다.

| ID | 수준 | 수용 기준 |
|---|---|---|
| AC-3.1 | MUST | 액세스 토큰이 유효하면 시스템은 토큰의 주인의 사용자 이름과 이메일을 **반드시** 돌려줘**야 한다**. |
| AC-3.2 | MUST | 액세스 토큰이 없으면 시스템은 **반드시** 조회를 거부**해야 한다**. |
| AC-3.3 | MUST | 액세스 토큰이 위조됐으면 시스템은 **반드시** 조회를 거부**해야 한다**. 액세스 토큰이 만료됐으면 시스템은 **반드시** 조회를 거부**해야 한다**. |
| AC-3.4 | MUST NOT | 시스템은 다른 회원의 정보를 **절대** 돌려줘**서는 안 된다**. 조회의 대상은 **반드시** 토큰의 주인이**어야 한다**. |
| AC-3.5 | MUST | 토큰이 유효해도 토큰의 주인인 회원이 없으면 시스템은 **반드시** 조회를 거부**해야 한다**. |

## 범위 밖

이 spec은 아래의 것을 요구하지 않는다.

- 회원 정보의 수정, 탈퇴
- 소개 글(`bio`)과 프로필 이미지(`image`). 원본에서는 가입 때 항상 비어 있다. 원본은 수정으로만 이 값을 채운다.
- 로그아웃, 토큰의 갱신
- 이메일의 인증, 비밀번호의 재설정

## 원본과 다른 점

| 항목 | 원본 | 이 spec | 이유 |
|---|---|---|---|
| 가입의 결과 | 토큰을 함께 준다 | 토큰을 주지 않는다 | 슬라이스에 로그인 단계가 따로 있다 |
| 사용자 이름과 이메일의 길이 | 상한이 없다 | 50자, 254자 | 상한이 없으면 "올바른 값"의 끝이 없다. 저장소의 한계가 서버의 오류로 나온다 |
| 가입 때 비밀번호의 길이 | 빈 값만 검사한다 | 8자 이상, 72바이트 이하 | 원본은 길이의 규칙을 수정에만 적용한다. 가입에도 같은 규칙이 맞다 |

## 확정한 가정

AI가 제안하고 사용자가 승인했다 (2026-11-16).

1. 시스템은 이메일의 대소문자를 **절대** 구분**해서는 안 된다**. `A@x.com`과 `a@x.com`은 같은 이메일이다.
2. 시스템은 사용자 이름의 대소문자를 **반드시** 구분**해야 한다**.
3. 시스템은 가입의 결과에 액세스 토큰을 **절대** 넣어**서는 안 된다**.
4. 비밀번호의 최대 길이는 UTF-8로 72바이트다 (AC-1.4). 처음에는 64자였다. 사용자가 BCrypt의 제한에 맞춰 바꿨다 (2026-11-17). 한글만 쓰면 24자까지다.
5. 사용자 이름의 최대 길이는 50자다. 이메일의 최대 길이는 254자다 (AC-1.9). 사용자가 정했다 (2026-11-17). 전에는 상한이 없었다. 256자 이상인 값으로 가입하면 서버의 오류가 났다.

## 받아들인 한계

아래의 두 가지는 결함이 아니다. 이 spec이 받아들였다.

- 가입의 결과(AC-1.5)는 이메일이 가입돼 있는지를 알려준다. AC-2.3의 보호는 로그인에만 있다. 원본도 같다.
- 로그인의 응답 시간은 경우마다 다른 경우가 있다. 이 spec은 응답 시간을 요구하지 않는다.

## 근거

| 의도 | 원본에서 읽은 곳 |
|---|---|
| 가입에 세 값이 필요하다, 빈 값과 틀린 형식을 거부한다 | `hurl/errors_auth.hurl` (Register empty/malformed) |
| 이메일과 사용자 이름은 유일하다 | `hurl/errors_auth.hurl` (Register duplicate) |
| 로그인 실패의 이유를 드러내지 않는다 | `hurl/errors_auth.hurl` (Login wrong password → `credentials invalid`) |
| 비밀번호는 8자 이상이다 | `hurl/errors_auth.hurl` (NIST 800-63B 주석) |
| 가입과 로그인에는 인증이 필요 없다 | `openapi.yml` (`security` 항목 없음). 킥오프 가설 2의 반례다 |
| 토큰이 없으면 내 정보를 조회하지 못한다 | `hurl/errors_auth.hurl` (GET /user no auth) |
