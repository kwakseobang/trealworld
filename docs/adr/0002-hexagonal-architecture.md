# ADR-0002. 헥사고날 아키텍처와 ArchUnit 규칙

- 상태: 승인 (2026-11-16). 스타일은 사용자가 결정했다. 세부 규칙은 AI가 제안하고 사용자가 승인했다.

## 맥락

도메인의 규칙([Domain 01](../domain/01-member.md))을 기술과 분리하고 싶다. 스택에 ArchUnit이 있다. 규칙을 문서가 아니라 테스트로 강제할 수 있다.

## 결정

헥사고날 아키텍처를 쓴다. 패키지는 세 부분이다.

| 패키지 | 내용 | 의존해도 되는 것 |
|---|---|---|
| `domain` | 회원, 값 객체, 도메인 규칙 | 없음 (Java, JPA 애너테이션, Lombok만) |
| `application` | 유스케이스, 포트(들어오는 것, 나가는 것) | `domain` |
| `adapter` | 웹, 영속성, 보안 | `application`, `domain` |

ArchUnit으로 강제하는 규칙:

1. `domain`은 `application`과 `adapter`에 의존하지 않는다.
2. `application`은 `adapter`에 의존하지 않는다.
3. `domain`은 Spring에 의존하지 않는다.
4. `adapter`끼리는 서로 의존하지 않는다. (웹은 영속성을 모른다.)
5. 웹 어댑터는 들어오는 포트를 통해서만 `application`을 쓴다.

도메인 엔티티에 JPA 애너테이션을 직접 붙인다. 영속성용 클래스를 따로 두지 않는다.

## 결과

- 좋은 점: 의존 방향이 테스트로 지켜진다. 도메인을 Spring 없이 테스트할 수 있다.
- 나쁜 점: 작은 슬라이스에 비해 파일과 인터페이스가 많다.
- 타협: 도메인이 JPA 애너테이션을 안다. 순수성은 줄고, 매핑 코드는 없어진다.

## 버린 대안

- 계층형, 기능별 패키지: 단순하다. 그러나 ArchUnit으로 강제할 규칙이 적다.
- 도메인 엔티티와 JPA 엔티티의 분리: 도메인이 순수해진다. 그러나 이 크기의 예제에는 매핑 코드가 과하다.
