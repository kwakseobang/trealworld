# ADR-0002. 헥사고날 아키텍처와 ArchUnit 규칙

- 상태: 승인 (2026-11-16). 스타일은 사용자가 결정했다. 세부 규칙은 AI가 제안하고 사용자가 승인했다. 수정 (2026-11-17): 포트의 위치를 적었다. 수정 (2026-11-17, 작업 2): 규칙이 쓰는 패키지의 이름을 적었다. 수정 (2026-11-17, 작업 4): 나머지 패키지의 이름과 조립하는 곳을 적었다. 수정 (2026-11-17): RFC 2119와 ASD-STE100의 원칙으로 다시 썼다. "JPA 애너테이션을 직접 붙인다"는 허용(MAY)으로 좁혔다 (일지의 스텝 43). 승인 (2026-11-17, 스텝 54): 작업 4에서 AI가 더한 결정과, AI가 좁힌 곳을 사용자가 AI의 권장대로 받아들였다. 하나씩 보지는 않았다. 목록은 일지의 스텝 54에 있다.
- 읽는 법: 굵게 쓴 **반드시 ~해야 한다**(MUST), **절대 ~해서는 안 된다**(MUST NOT), **~하는 것을 권장한다**(SHOULD), **~할 수 있다**(MAY)는 RFC 2119의 뜻이다. 표는 [Spec 01](../spec/01-member-signup-login.md#이-문서를-읽는-법)에 있다. 굵은 말이 없는 문장은 설명이다.

## 맥락

도메인의 규칙([Domain 01](../domain/01-member.md))을 기술과 분리한다. 스택에 ArchUnit이 있다. ArchUnit은 규칙을 테스트로 강제한다. 문서만으로는 규칙을 강제하지 못한다.

## 결정

이 프로젝트는 헥사고날 아키텍처를 **반드시** 써**야 한다**. 패키지는 세 부분이다.

| 패키지 | 내용 | 의존**할 수 있다** (MAY) |
|---|---|---|
| `domain` | 회원, 값 객체, 도메인 규칙 | Java, JPA 애너테이션, Lombok. 다른 것은 없다 |
| `application` | 유스케이스, 포트(들어오는 것, 나가는 것) | `domain` |
| `adapter` | 웹, 영속성, 보안 | `application`, `domain` |

ArchUnit으로 강제하는 규칙:

| # | 수준 | 규칙 |
|---|---|---|
| 1 | MUST NOT | `domain`은 `application`과 `adapter`에 **절대** 의존**해서는 안 된다**. |
| 2 | MUST NOT | `application`은 `adapter`에 **절대** 의존**해서는 안 된다**. |
| 3 | MUST NOT | `domain`은 Spring에 **절대** 의존**해서는 안 된다**. |
| 4 | MUST NOT | adapter 하나는 다른 adapter에 **절대** 의존**해서는 안 된다**. (웹은 영속성을 모른다.) |
| 5 | MUST | 웹 어댑터는 **반드시** 들어오는 포트를 통해서만 `application`을 써**야 한다**. |

- 규칙 1~5는 **반드시** `ArchitectureTests`에 테스트로 있**어야 한다**.
- 테스트의 이름에는 **반드시** 규칙의 번호가 있**어야 한다**.

포트의 위치:

- 포트는 모두 **반드시** `application`에 두**어야 한다**.
- `domain`에는 인터페이스를 **절대** 두**어서는 안 된다**.

규칙이 쓰는 패키지의 이름 (기본 패키지는 `trealworld`). 코드는 이 이름을 **반드시** 써**야 한다**.

| 규칙의 말 | 패키지 |
|---|---|
| 들어오는 포트 | `application.port.in` |
| 나가는 포트 | `application.port.out` |
| 유스케이스의 구현 | `application.service` |
| 웹 어댑터 | `adapter.web` |
| adapter 하나 | `adapter`의 바로 아래 패키지 하나 (`adapter.web`, `adapter.persistence`, `adapter.security`) |

`application`과 Spring:

- `application`은 Spring을 **절대** 써**서는 안 된다**.
- 기본 패키지의 `UseCaseConfig`가 유스케이스를 **반드시** 빈으로 등록**해야 한다**.
- 유스케이스가 던지는 예외는 **반드시** 들어오는 포트의 패키지에 두**어야 한다**. 웹 어댑터가 그 예외를 알아야 하기 때문이다.

도메인과 JPA:

- 도메인 엔티티에 JPA 애너테이션을 직접 붙**일 수 있다**.
- 영속성용 클래스를 따로 **절대** 두**어서는 안 된다**.

## 결과

- 좋은 점: 테스트가 의존의 방향을 지킨다. 도메인의 테스트는 Spring 없이 돈다.
- 나쁜 점: 작은 슬라이스에 비해 파일과 인터페이스가 많다.
- 타협: 도메인이 JPA 애너테이션을 안다. 순수성은 줄고, 매핑 코드는 없어진다.

## 버린 대안

- 계층형, 기능별 패키지: 단순하다. 그러나 ArchUnit으로 강제할 규칙이 적다.
- 도메인 엔티티와 JPA 엔티티의 분리: 도메인이 순수해진다. 그러나 이 크기의 예제에는 매핑 코드가 과하다.
