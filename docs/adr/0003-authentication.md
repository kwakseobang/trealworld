# ADR-0003. 인증: JWT와 Spring Security

- 상태: 승인 (2026-11-16). 방식은 사용자가 결정했다. 세부 값은 AI가 제안하고 사용자가 승인했다. 수정 (2026-11-17): BCrypt의 길이 제한, 시계, 인증 실패의 응답을 적었다. 수정 (2026-11-17, 작업 5): JWT 라이브러리, 서명, 서명 키의 설정을 적었다.

## 맥락

[Spec 01](../spec/01-member-signup-login.md)의 목표 2와 3에 액세스 토큰이 필요하다. 가입과 로그인은 인증 없이 되어야 한다.

## 결정

- 액세스 토큰은 JWT다. 서버는 토큰을 저장하지 않는다.
- Spring Security를 쓴다. 필터 체인이 토큰을 검사한다.
- 토큰은 `Authorization: Bearer <토큰>` 헤더로 받는다.
- 토큰에는 회원의 식별자(`sub`)와 만료 시각(`exp`)만 넣는다. 유효 시간은 1시간이다.
- JWT 라이브러리는 Spring Security의 `spring-security-oauth2-jose`다. 서명은 HS256이다.
- 비밀번호는 Spring Security의 `PasswordEncoder`(BCrypt)로 해시한다. BCrypt는 입력의 앞 72바이트만 쓴다. 그래서 비밀번호를 72바이트로 제한한다 (Domain R4).
- 가입과 로그인만 인증 없이 허용한다. 나머지는 모두 인증이 필요하다.
- 세션과 CSRF 보호는 끈다. 상태가 없는 API이기 때문이다.
- 토큰이 유효해도 그 주인인 회원이 없으면 인증 실패다 (AC-3.5).
- 인증에 실패하면 보안 어댑터가 401을 응답한다. 본문은 [ADR-0005](0005-api-conventions.md)의 오류 형식이다.
- 현재 시각은 주입하는 `Clock`에서 읽는다. 테스트는 시각을 바꿔서 만료를 확인한다.

헥사고날 구조에서의 위치:

- 비밀번호 해시와 토큰 발급은 `application`의 나가는 포트다.
- Spring Security와 JWT 라이브러리는 `adapter`의 보안 부분에만 있다. `domain`과 `application`은 이것을 모른다.

## 결과

- 좋은 점: 서버에 상태가 없다. 원본의 아이디어와 같다.
- 나쁜 점: 발급한 토큰을 만료 전에 취소할 수 없다. 로그아웃이 없다. 범위 밖이므로 받아들인다.
- 나쁜 점: 기술의 제한(72바이트)이 도메인 규칙에 들어갔다. 한글만 쓴 비밀번호는 24자까지다. 사용자가 선택했다.
- 서명 키는 설정 `trealworld.jwt.secret`에서 읽는다. UTF-8로 32바이트 이상이어야 한다. 저장소에 실제 키를 넣지 않는다.
- 서명 키가 없으면 서버는 시작할 때 임의의 키를 만들고 경고를 남긴다. 서버를 다시 시작하면 발급한 토큰은 모두 무효가 된다. 서버가 여러 대이면 키를 반드시 설정해야 한다.

## 버린 대안

- JWT를 직접 구현: 보안 코드를 직접 만들게 된다.
- 서버 저장 토큰: 취소는 쉽다. 요청마다 DB를 조회한다.
- HTTP 세션: 가장 단순하다. 원본의 토큰 방식과 다르다.
- 해시를 Argon2id나 PBKDF2로 바꾸는 것: 길이 제한이 없어서 규칙(64자)을 지킬 수 있다. 사용자는 BCrypt를 유지하고 규칙을 바꾸는 쪽을 골랐다.
