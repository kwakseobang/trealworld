# ADR-0003. 인증: JWT와 Spring Security

- 상태: 승인 (2026-11-16). 방식은 사용자가 결정했다. 세부 값은 AI가 제안하고 사용자가 승인했다. 수정 (2026-11-17): BCrypt의 길이 제한, 시계, 인증 실패의 응답을 적었다. 수정 (2026-11-17, 작업 5): JWT 라이브러리, 서명, 서명 키의 설정을 적었다. 수정 (2026-11-17): RFC 2119와 ASD-STE100의 원칙으로 다시 썼다. 결정의 뜻은 바꾸지 않았다.
- 읽는 법: 굵게 쓴 **반드시 ~해야 한다**(MUST), **절대 ~해서는 안 된다**(MUST NOT), **~하는 것을 권장한다**(SHOULD), **~할 수 있다**(MAY)는 RFC 2119의 뜻이다. 표는 [Spec 01](../spec/01-member-signup-login.md#이-문서를-읽는-법)에 있다. 굵은 말이 없는 문장은 설명이다.

## 맥락

[Spec 01](../spec/01-member-signup-login.md)의 목표 2와 3에 액세스 토큰이 필요하다. 가입과 로그인에는 인증이 필요 없다.

## 결정

액세스 토큰:

- 액세스 토큰은 **반드시** JWT**여야 한다**.
- 서버는 토큰을 **절대** 저장**해서는 안 된다**.
- 토큰에는 회원의 식별자(`sub`)와 만료 시각(`exp`)을 **반드시** 넣**어야 한다**. 다른 값은 **절대** 넣어**서는 안 된다**.
- 토큰의 유효 시간은 **반드시** 1시간이**어야 한다**.
- JWT 라이브러리는 **반드시** Spring Security의 `spring-security-oauth2-jose`**여야 한다**.
- 서명은 **반드시** HS256이**어야 한다**.

서명 키:

- 서버는 서명 키를 **반드시** 설정 `trealworld.jwt.secret`에서 읽**어야 한다**.
- 서명 키는 **반드시** UTF-8로 32바이트 이상이**어야 한다**. 더 짧으면 서버는 시작을 **반드시** 거부**해야 한다**.
- 저장소에 실제 키를 **절대** 넣어**서는 안 된다**.
- 서명 키가 없으면 서버는 시작할 때 임의의 키를 **반드시** 만들**어야 한다**. 서버는 경고를 **반드시** 남겨**야 한다**. 이 경우에 서버를 다시 시작하면 발급한 토큰은 모두 무효가 된다.
- 서버가 여러 대이면 서명 키를 **반드시** 설정**해야 한다**.

요청의 인증:

- 이 프로젝트는 Spring Security를 **반드시** 써**야 한다**. 필터 체인이 토큰을 **반드시** 검사**해야 한다**.
- 서버는 토큰을 **반드시** `Authorization: Bearer <토큰>` 헤더로 받**아야 한다**.
- 서버는 가입과 로그인을 인증 없이 **반드시** 받아들여**야 한다**. 나머지 요청에는 **반드시** 인증을 요구**해야 한다**.
- 세션과 CSRF 보호는 **반드시** 꺼**야 한다**. 상태가 없는 API이기 때문이다.
- 토큰이 유효해도 토큰의 주인인 회원이 없으면 서버는 **반드시** 인증 실패로 처리**해야 한다** (AC-3.5).
- 인증에 실패하면 보안 어댑터가 **반드시** 401을 응답**해야 한다**. 본문은 **반드시** [ADR-0005](0005-api-conventions.md)의 오류 형식이**어야 한다**.

비밀번호:

- 비밀번호는 **반드시** Spring Security의 `PasswordEncoder`(BCrypt)로 해시**해야 한다**.
- BCrypt는 입력의 앞 72바이트만 쓴다. 그래서 비밀번호를 72바이트로 제한한다 (Domain R4).

시각:

- 코드는 현재 시각을 **반드시** 주입하는 `Clock`에서 읽**어야 한다**.
- 테스트는 `Clock`을 바꿔서 만료를 확인**할 수 있다**.

헥사고날 구조에서의 위치:

- 비밀번호 해시와 토큰의 발급은 **반드시** `application`의 나가는 포트**여야 한다**.
- Spring Security와 JWT 라이브러리는 **반드시** `adapter`의 보안 부분에만 두**어야 한다**. `domain`과 `application`은 이 둘에 **절대** 의존**해서는 안 된다**.

## 결과

- 좋은 점: 서버에 상태가 없다. 원본의 아이디어와 같다.
- 나쁜 점: 서버는 발급한 토큰을 만료 전에 취소하지 못한다. 로그아웃이 없다. 범위 밖이므로 받아들인다.
- 나쁜 점: 기술의 제한(72바이트)이 도메인 규칙에 들어갔다. 한글만 쓴 비밀번호는 24자까지다. 사용자가 선택했다.

## 버린 대안

- JWT를 직접 구현: 보안 코드를 직접 만들게 된다.
- 서버 저장 토큰: 취소는 쉽다. 요청마다 DB를 조회한다.
- HTTP 세션: 가장 단순하다. 원본의 토큰 방식과 다르다.
- 해시를 Argon2id나 PBKDF2로 바꾸는 것: 길이 제한이 없다. 처음의 규칙(64자)이 그대로 남는다. 사용자는 BCrypt를 유지하고 규칙을 바꾸는 쪽을 골랐다.
