# ADR-0005. API 규약

- 상태: 승인 (2026-11-16). AI가 제안하고 사용자가 승인했다. 수정 (2026-11-17): 401의 본문과 응답 객체를 적었다. 수정 (2026-11-17, 작업 4): `errors`의 모양을 적었다. 수정 (2026-11-17, 작업 5): 로그인의 응답과 400의 범위를 적었다. 수정 (2026-11-17): RFC 2119와 ASD-STE100의 원칙으로 다시 썼다. 문장의 뜻은 바꾸지 않았다. 수정 (2026-11-17, 문서와 코드의 대조): 500을 적었다. 수정 (2026-11-17, 작업 6): 조회의 응답을 적었다. 수정 (2026-11-17, 작업 6의 리뷰): 컨트롤러에 닿지 않은 요청의 오류를 적었다. 승인 (2026-11-17, 스텝 54): 작업 4 ~ 6과 그 리뷰에서 AI가 더한 결정을 사용자가 AI의 권장대로 받아들였다. 하나씩 보지는 않았다. 목록은 일지의 스텝 54에 있다. 수정 (2026-11-19, 일지의 스텝 78): codex의 리뷰를 반영했다. 목록은 [리뷰 처리 문서](../review/2026-11-19-review-handling.md)에 있다. 요청의 필드와 읽지 못하는 본문을 적었다. 수정 (2026-11-19, 일지의 스텝 79): 리뷰가 남긴 결정을 AI가 정했다. 사용자가 AI의 권장을 따르기로 했다. 하나씩 보지는 않았다. 목록은 [리뷰 처리 문서](../review/2026-11-19-review-handling.md)의 "결정"에 있다. 문자열이 아닌 값, 404와 405, `instance`의 값을 적었다. 문자열이 아닌 값은 동작을 바꿨다: 앞에는 글자로 바꿔서 받았다.
- 읽는 법: 굵게 쓴 **반드시 ~해야 한다**(MUST), **절대 ~해서는 안 된다**(MUST NOT), **~하는 것을 권장한다**(SHOULD), **~할 수 있다**(MAY)는 RFC 2119의 뜻이다. 표는 [Spec 01](../spec/01-member-signup-login.md#이-문서를-읽는-법)에 있다. 굵은 말이 없는 문장은 설명이다.

## 맥락

이 프로젝트에는 원본의 API의 모양을 따를 의무가 없다 (킥오프 6.6). Spec은 API의 모양을 정하지 않는다. 그래서 여기에서 정한다.

## 결정

서버는 아래의 경로와 상태 코드를 **반드시** 써**야 한다**.

| 목표 | 요청 | 성공 |
|---|---|---|
| 가입 | `POST /api/members` | 201 |
| 로그인 | `POST /api/auth/login` | 200 |
| 내 정보 조회 | `GET /api/members/me` | 200 |

| 실패의 경우 | 코드 |
|---|---|
| 값이 비었거나 형식이 틀리다 | 400 |
| 로그인 실패, 토큰이 없거나 틀리다 | 401 |
| 이메일이나 사용자 이름이 이미 있다 | 409 |
| 서버가 받아들이지 않는 경로 (예: `;`, `//`가 있다) | 400 |
| 읽지 못하는 본문 | 400 |
| 없는 경로 (인증한 요청) | 404 |
| 그 경로가 받지 않는 메서드 (인증한 요청) | 405 |
| 예상하지 못한 오류 | 500 |

본문의 형식:

- 요청과 응답의 본문은 **반드시** JSON이**어야 한다**.
- 요청의 필드는 아래와 같다. 값은 모두 JSON의 문자열이다.

  | 요청 | 필드 | 예 |
  |---|---|---|
  | 가입 | `username`, `email`, `password` | `{"username": "jake", "email": "jake@example.com", "password": "correct-horse-battery"}` |
  | 로그인 | `email`, `password` | `{"email": "jake@example.com", "password": "correct-horse-battery"}` |

- 서버는 표에 없는 필드를 무시한다.
- 서버는 문자열이 아닌 값(숫자, 참거짓, 객체, 배열)을 글자로 바꿔서 **절대** 받아**서는 안 된다**. 바꿔서 받으면 `{"password": 12345678}`이 비밀번호 `"12345678"`이 된다. 그런 값이 있는 본문은 읽지 못하는 본문이다.
- 읽지 못하는 본문은 **반드시** 400이**어야 한다**. 이 400의 본문에는 `errors`가 없다. 서버가 필드를 알지 못한다. 예: JSON이 아니다, 값이 문자열이 아니다.
- 서버는 요청의 본문의 크기를 제한하지 않는다. 받아들인 한계다 ([Spec 01](../spec/01-member-signup-login.md#받아들인-한계)).
- 원본의 `{"user": {...}}` 같은 겉껍질은 **절대** 써**서는 안 된다**.
- 응답은 **반드시** 응답용 객체로 만들**어야 한다**. 도메인 엔티티를 **절대** 그대로 내보내**서는 안 된다**. 회원 엔티티에는 비밀번호 해시가 있다.

오류의 본문:

- 오류의 본문은 **반드시** RFC 9457 Problem Details 형식이**어야 한다**. Spring의 `ProblemDetail`을 쓴다.
- 값의 오류(400)의 본문에는 **반드시** `errors`를 넣**어야 한다**. `errors`는 필드의 이름과 이유의 맵이다. 예: `{"errors": {"email": "이메일의 형식이 올바르지 않다"}}`.
- 409의 본문에도 같은 모양의 `errors`를 **반드시** 넣**어야 한다**.
- 예상하지 못한 오류(500)의 본문도 **반드시** 같은 오류 형식이**어야 한다**. 본문에는 오류의 원인을 **절대** 넣어**서는 안 된다**. 원인은 로그에만 남긴다 (AC-1.7).
- 컨트롤러에 닿지 않은 요청의 오류도 **반드시** 같은 오류 형식이**어야 한다**. 예: 필터의 안에서 난 예외(500), 서버가 받아들이지 않는 경로(400). 웹 어댑터의 오류의 화면(`/error`)이 이 본문을 만든다. Spring Boot의 기본 오류 본문은 **절대** 내보내**서는 안 된다**.
- 오류의 본문의 `instance`는 **반드시** 오류가 난 요청의 경로**여야 한다**. `/error`가 아니다. 경로는 클라이언트가 보낸 그대로다 (예: `/api/members/me;x=1`).
- 서버의 오류(500)는 **절대** 401로 응답**해서는 안 된다**.
- Spring Security의 필터가 거부한 요청(401)의 본문도 **반드시** 같은 오류 형식이**어야 한다**. 컨트롤러의 예외 처리는 필터에 닿지 않는다. 그래서 보안 어댑터가 이 본문을 따로 만든다.

가입과 조회:

- 가입의 응답과 내 정보 조회의 응답은 **반드시** `{"username": "…", "email": "…"}`이**어야 한다**. 다른 값은 **절대** 넣어**서는 안 된다**.
- 내 정보 조회는 요청의 경로, 쿼리, 본문에서 조회의 대상을 **절대** 읽어**서는 안 된다**. 대상은 토큰의 주인이다 (AC-3.4).

로그인:

- 로그인의 응답은 **반드시** `{"accessToken": "<토큰>"}`이**어야 한다**. 다른 값은 **절대** 넣어**서는 안 된다**.
- 로그인에서 값의 오류(400)는 두 가지다.
  - 이메일이 비었거나 형식이 틀리거나 254자보다 길다 (R2).
  - 비밀번호가 없거나 빈 글자(`""`)다.
- 로그인은 비밀번호의 길이를 **절대** 값의 오류로 알려**서는 안 된다**. 가입하지 못하는 길이의 비밀번호는 로그인 실패(401)다.
- 로그인 실패(401)의 본문에는 `errors`를 **절대** 넣어**서는 안 된다**. 서버는 어느 값이 틀렸는지 알려주지 않는다.

## 결과

- 원본과 다른 점: 경로(`/users` → `/members`), 겉껍질 없음, 값의 오류 422 → 400, 오류 형식.
- 원본의 Hurl 테스트는 이 API에서 통과하지 않는다. 의도한 것이다.

## 버린 대안

- 원본의 모양을 그대로 쓴다: 호환은 목표가 아니다. 도메인 용어(회원)와 경로(`users`)가 어긋난다.
