# ADR-0004. 검증: 테스트 먼저 (TDD)

- 상태: 승인 (사용자가 결정, 2026-11-16). 수정 (2026-11-17): RFC 2119와 ASD-STE100의 원칙으로 다시 썼다. 결정의 뜻은 바꾸지 않았다. 수정 (2026-11-17, 문서와 코드의 대조): 테스트의 이름에 쓰는 ID의 종류를 적었다.
- 읽는 법: 굵게 쓴 **반드시 ~해야 한다**(MUST), **절대 ~해서는 안 된다**(MUST NOT), **~하는 것을 권장한다**(SHOULD), **~할 수 있다**(MAY)는 RFC 2119의 뜻이다. 표는 [Spec 01](../spec/01-member-signup-login.md#이-문서를-읽는-법)에 있다. 굵은 말이 없는 문장은 설명이다.

## 맥락

이 프로젝트는 원본의 Hurl 테스트를 수용 테스트로 쓰지 않는다 (킥오프 6.6). 그래서 "무엇으로 검증하는가"가 빈칸이었다 (킥오프 열린 질문 8).

## 결정

테스트를 **반드시** 구현보다 먼저 써**야 한다**. 테스트는 세 종류다.

| 종류 | 무엇을 검증하는가 | 출처 |
|---|---|---|
| 수용 테스트 | HTTP 요청과 응답. 서버 전체를 띄운다 | Spec의 수용 기준 (AC) |
| 도메인 단위 테스트 | 도메인의 규칙. Spring 없이 돈다 | Domain의 규칙 (R) |
| 아키텍처 테스트 | 의존의 방향 | [ADR-0002](0002-hexagonal-architecture.md)의 규칙 |

- 순서는 **반드시** 아래와 같**아야 한다**.
  1. 수용 테스트를 쓴다. 테스트가 실패한다.
  2. 도메인 단위 테스트를 쓴다. 테스트가 실패한다.
  3. 구현한다.
  4. 테스트가 통과한다.
  5. 정리한다.
- 수용 테스트는 **반드시** 서버 전체를 띄워**야 한다**.
- 도메인 단위 테스트는 Spring을 **절대** 써**서는 안 된다**.
- 테스트의 이름에는 ID를 **반드시** 넣**어야 한다**. ID는 테스트가 검증하는 문장의 것이다: 수용 기준(`ac1_1_`), 도메인 규칙(`r1_`), ADR-0002의 규칙(`rule1_`), 다른 ADR의 결정(`adr0003_`).
- `ArchitectureTests`가 이 규칙을 **반드시** 검사**해야 한다**.
- 수용 기준 하나에는 테스트가 **반드시** 하나 이상 있**어야 한다**.

## 결과

- 좋은 점: spec → 테스트 → 코드의 연결이 ID로 보인다. 발표에서 이 연결을 따라간다.
- 나쁜 점: 수용 테스트는 서버를 띄우므로 느리다. 슬라이스가 작아서 받아들인다.

## 버린 대안

- 구현 후 테스트: 빠르다. spec과 코드의 연결이 약해진다.
- 수용 테스트만: 도메인의 규칙을 HTTP를 거쳐서만 확인하게 된다.
