# ADR-0004. 검증: 테스트 먼저 (TDD)

- 상태: 승인 (사용자가 결정, 2026-11-16)

## 맥락

원본의 Hurl 테스트를 수용 테스트로 쓰지 않는다 (킥오프 6.6). 그래서 "무엇으로 검증하는가"가 빈칸이었다 (킥오프 열린 질문 8).

## 결정

테스트를 먼저 쓴다. 테스트는 세 종류다.

| 종류 | 무엇을 검증하는가 | 출처 |
|---|---|---|
| 수용 테스트 | HTTP 요청과 응답. 서버 전체를 띄운다 | Spec의 수용 기준 (AC) |
| 도메인 단위 테스트 | 도메인의 규칙. Spring 없이 돈다 | Domain의 규칙 (R) |
| 아키텍처 테스트 | 의존 방향 | [ADR-0002](0002-hexagonal-architecture.md)의 규칙 |

- 순서: 수용 테스트(실패) → 도메인 단위 테스트(실패) → 구현 → 통과 → 정리.
- 테스트의 이름에 AC나 R의 ID를 넣는다. 수용 기준 하나에 테스트가 하나 이상 있다.

## 결과

- 좋은 점: spec → 테스트 → 코드의 연결이 ID로 보인다. 발표에서 추적할 수 있다.
- 나쁜 점: 수용 테스트는 서버를 띄우므로 느리다. 슬라이스가 작아서 받아들인다.

## 버린 대안

- 구현 후 테스트: 빠르다. spec과 코드의 연결이 약해진다.
- 수용 테스트만: 도메인의 규칙을 HTTP를 거쳐서만 확인하게 된다.
