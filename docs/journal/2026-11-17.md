     | 어댑터 | `MemberPersistenceAdapterTests` (3개) | 유스케이스를 거치지 않고 같은 값을 두 번 저장한다 |

  2. 돌렸다. 5개가 실패했다. 나머지 88개는 통과했다.

  4. `./gradlew clean build`를 돌렸다. 94개가 통과했다. 수용 테스트를 3번 더 돌렸다. 모두 통과했다.
  5. 서버를 띄우고 스텝 37의 실험을 다시 했다.
- **고친 방법**
  - 나가는 포트에 예외를 더했다: `MemberNotUniqueException` (`application.port.out`). 뜻: "이메일이나 사용자 이름이 이미 있다. 어느 값인지는 모른다."
  - 영속성 어댑터는 DB의 제약이 저장을 거부하면 이 예외로 바꾼다.
  - 유스케이스는 이 예외를 받으면 저장소에 다시 묻는다 (`existsByEmail`, `existsByUsername`). 먼저 저장한 가입은 이미 커밋했다. 그래서 "있다"가 나온다. `DuplicateMemberException`을 던진다. 웹 어댑터는 바뀌지 않았다.
  - 다시 물어도 없으면 중복이 아니다. 예외를 그대로 던진다. 숨기지 않는다.
- **검증** (서버에서, 요청 12개를 동시에)

  | 실험 | 고치기 전 (스텝 37) | 고친 뒤 |
  |---|---|---|
  | 같은 값 (3번 반복) | 201이 1개, 409가 2개, 500이 9개 | 3번 모두 201이 1개, 409가 11개 |
  | 같은 이메일, 다른 사용자 이름 | (하지 않았다) | 201이 1개, 409가 11개 |
  | 같은 사용자 이름, 다른 이메일 | (하지 않았다) | 201이 1개, 409가 11개 |
  | 300자인 사용자 이름 (메모 2) | 500 | 500 (그대로다. 고치지 않았다) |

  테스트의 수: 87개 → 94개. 수용 +1, 유스케이스 +3, 어댑터 +3.

- **결정 (AI)**
  - 어댑터는 "어느 제약이 깨졌는가"를 읽지 않는다. 제약의 이름과 오류 메시지는 DB마다 다르다. 유스케이스가 이미 가진 질문(`existsBy…`)으로 답을 얻는다.
  - 예외는 `port.out`에 둔다. 저장소의 약속의 일부다. `MemberRepository.save`의 주석에 적었다.
  - 어댑터는 `saveAndFlush`를 쓴다. 제약의 위반이 `save()`의 안에서 나게 한다.
  - 영속성 어댑터의 테스트를 처음 만들었다. 포트의 약속을 실제 DB로 확인한다. unique 제약의 테스트가 생겼다 (스텝 37의 메모 7의 일부).
- **버린 대안**
  - 웹 어댑터가 `DataIntegrityViolationException`을 409로 바꾸는 것. 가장 짧다. 그러나 웹 어댑터가 영속성 기술의 예외를 알게 된다 (규칙 4의 뜻을 어긴다). 어느 값인지도 알 수 없다.
  - 어댑터가 제약의 이름을 읽어서 필드를 정하는 것. 다시 묻는 질의가 없다. DB와 매핑에 묶인다.
  - 가입을 직렬화하는 것 (잠금, `SERIALIZABLE`). 경주가 없어진다. 가입이 느려지고, DB의 기능에 기댄다.
- **남은 일**
  - 메모 2(긴 값의 500)는 그대로다. 이제 `MemberNotUniqueException`으로 싸여서 500이 된다. 이름이 사실과 다르다. 메모 2를 고칠 때 함께 본다.
  - 유스케이스에 트랜잭션을 씌우면 이 방법은 다시 봐야 한다. 실패한 저장의 뒤에 같은 트랜잭션에서 다시 물을 수 없다.
  - 500의 본문은 아직 Problem Details가 아니다.
- **관찰**
  - 같은 결함을 세 층의 테스트가 다른 방법으로 잡는다. 수용 테스트는 실제 경주를 만든다 (확률에 기댄다. 고치기 전에는 12개 중 9개가 실패했다). 유스케이스의 테스트는 경주를 가짜 저장소로 **정확히** 만든다 (항상 같은 결과다). 포트가 있어서 "그 사이에 다른 가입이 저장한다"를 한 줄로 흉내 낼 수 있었다.
  - 고친 곳은 `application`과 `adapter.persistence`다. `adapter.web`과 `domain`은 바뀌지 않았다. 응답의 모양(409, `errors`)도 그대로다. 층의 경계가 변경의 범위를 정했다.
  - 리뷰 → 실험 → 결함의 확인 → 수정의 한 주기가 한 스텝에서 닫혔다. 설명 문서(`ea4c75e`)의 메모 1은 그 커밋에 대해서는 여전히 맞다.
