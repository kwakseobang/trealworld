## 스텝 42. Spec 01과 Domain 01을 RFC 2119와 ASD-STE100의 원칙으로 다시 씀

- **질문 1**: spec이 RFC 2119를 잘 준수했는가.
- **답 (AI)**: 아니다. Spec 01에는 키워드가 0개였다. 수용 기준 18개가 모두 평서문이었다. 문제는 3개였다. (1) "~할 수 있다"를 가능성의 뜻으로 썼다. (2) 요구의 수준을 문장에서 읽지 못한다. (3) 범위가 흐린 말이 있다 (AC-2.4의 "비어 있거나", AC-2.3의 "구분할 수 없는 결과"). Domain 01과 ADR도 같았다.
- **질문 2**: RFC 2119와 ASD-STE100을 동시에 적용하는 것이 가능한가.
- **답 (AI)**: 가능하다. RFC 2119는 요구의 수준을 다룬다. STE100은 문장의 모양을 다룬다. 충돌은 2개다. (1) 영어의 낱말: STE100의 사전은 `shall`, `should`, `may`를 허용하지 않는다 (AI의 기억이다. 확인하지 않았다). 한국어 문서에는 해당하지 않는다. (2) SHOULD는 STE100의 눈에 모호하다. 예외의 조건을 함께 적어서 푼다.
- **요청**: spec과 도메인 문서를 RFC 2119와 STE100의 원칙으로 다시 쓴다.
- **한 일**
  1. Spec 01을 다시 썼다. 수용 기준 18개와 "확정한 가정" 3개에 키워드를 넣었다.
  2. Domain 01을 다시 썼다. 규칙 10개, 용어의 규칙, 포트의 위치에 키워드를 넣었다.
  3. 두 문서에 "이 문서를 읽는 법"을 더했다. 키워드의 뜻, "~할 수 있다"의 뜻, "시스템", "결과", "거부한다"의 뜻이다.
  4. 표에 "수준"의 열을 더했다 (MUST, MUST NOT).
  5. 스크립트로 검사했다.
- **검사의 결과**

  | 항목 | Spec 01 | Domain 01 |
  |---|---|---|
  | ID의 수 | 18 (그대로) | 10 (그대로) |
  | "반드시" | 27 | 12 |
  | "절대" | 5 | 8 |
  | SHOULD, MAY인 요구 | 0 | 0 |
  | "~할 수 있다" (키워드의 설명 밖) | 0 | 0 |
  | 표의 수준과 문장의 키워드 | 모두 맞다 | 모두 맞다 |

- **쓴 규칙**
  - 문장의 주어를 적는다 ("시스템은"). 한 문장에 요구는 하나다. "A이거나 B이면"은 두 문장으로 나눈다 (AC-1.4, AC-2.4, AC-3.3).
  - "~할 수 있다", "~할 수 없다"를 능력과 가능성의 뜻으로 쓰지 않는다. "조회할 수 없다" → "절대 돌려줘서는 안 된다". "다를 수 있다" → "다른 경우가 있다".
  - 금지는 MUST NOT으로 쓴다. 부정의 평서문("들어 있지 않다")으로 쓰지 않는다.
  - 굵은 말이 없는 문장은 설명이다. 용어의 표, 모델, 범위 밖, 근거에는 키워드를 넣지 않았다. RFC 2119는 키워드를 아껴 쓰라고 한다.
- **결정 (AI)**
  - 요구는 모두 MUST나 MUST NOT이다. SHOULD와 MAY는 하나도 없다. 원래의 문장에 "권장"이나 "허용"의 뜻이 없었다. 새로 만들지 않았다.
  - ID는 바꾸지 않았다. 테스트의 이름이 ID를 쓴다.
  - ADR은 고치지 않았다. 요청은 spec과 도메인 문서다.
- **뜻이 더 좁아진 곳 (사용자의 확인이 필요하다)**. 다시 쓰는 일은 흐린 말을 고르게 만든다. 아래의 4곳에서 AI가 뜻을 골랐다.

  | 곳 | 전 | 후 | 근거 |
  |---|---|---|---|
  | AC-2.3 | "AC-2.2와 구분할 수 없는 결과를 준다" | "결과의 내용은 반드시 같아야 한다. 응답 시간은 대상이 아니다" | 같은 문서의 "받아들인 한계" |
  | R3 | "비어 있지 않다. 앞뒤 공백을 지운다" | "한 자 이상이어야 한다. 길이는 공백을 지운 뒤에 센다" | 코드(`Username`)와 테스트 |
  | "거부한다" | 뜻이 없었다 | "요청한 일을 하지 않는다. 거부한 것을 결과로 알려준다" | 모든 AC의 테스트 |
  | 가정 3 | "가입은 토큰을 주지 않는다" | "절대 넣어서는 안 된다" (MUST NOT) | "원본과 다른 점"의 표 |

- **고르지 않은 곳**: AC-1.2와 AC-2.4의 "비어 있다". 뜻을 정하지 않았다. 작업 5의 결정(없는 값과 `""`만 400, 공백뿐인 비밀번호는 401)은 아직 사용자의 확인을 받지 않았다. 확인을 받으면 spec에 뜻을 적는다. "이메일의 형식이 틀리다"와 "유효한 액세스 토큰"도 뜻이 없다.
- **버린 대안**
  - 머리에 "수용 기준은 모두 MUST다"를 한 줄 적고 문장은 그대로 두는 것. 변경이 작다. MUST NOT인 문장과 "수 있다"는 따로 고쳐야 한다. 사용자가 "다시 작성"을 요청했다.
  - 영어의 키워드(MUST)를 문장에 넣는 것. 전역 규칙이 한국어의 말을 정했다. 영어는 "수준"의 열에만 넣었다.
- **관찰**
  - 수용 기준 18개 중 MUST NOT은 2개다 (AC-1.7, AC-3.4). 도메인 규칙 10개 중 MUST NOT은 5개다 (R5, R6, R7, R9, R10). 도메인의 규칙은 금지가 반이다. spec은 "무엇을 한다"를 말하고 도메인은 "무엇이 깨지면 안 된다"(불변식)를 말한다. 수준의 열이 이것을 보여준다.
  - "한 문장에 요구 하나"로 나누면 AC 하나에 MUST가 2~4개다. AC-2.4에는 4개다. 테스트의 수와 가까워진다. AC-2.4의 테스트는 3개다 (빈 값, 모든 빈 값, 형식).
  - 문서를 다시 쓰는 일이 리뷰가 됐다. 주어를 적으려면 "누가 거부하는가"를, MUST를 적으려면 "예외가 없는가"를 답해야 한다. 뜻이 좁아진 4곳은 모두 이 질문에서 나왔다.
  - 코드와 테스트는 바뀌지 않았다. 문서의 말투만 바뀌었다. 그러나 AC-2.3의 새 문장("내용이 같아야 한다")은 이미 있는 테스트(`ac2_3_…cannot_be_told_from_a_wrong_password`)와 정확히 같은 것을 말한다. 테스트가 spec보다 먼저 분명했다.

## 스텝 52. 서버의 오류가 401로 보이는 결함을 고침

- **질문 (AI)**: 서버의 오류가 401로 보이는 것을 고칠까.
- **답 (사용자)**: 고친다.
- **한 일 (순서대로)**
  1. 지금의 서버에서 같은 증상이 다른 곳에도 있는지 봤다. 있었다 (아래).
  2. 실패하는 수용 테스트를 썼다 (새 클래스 2개, 9개). 돌렸다. 7개가 실패했다. 이유를 봤다: 400이나 500을 기대하는데 401이 온다. 맞는 이유다.
  3. 고쳤다.
  4. `./gradlew clean build`를 돌렸다. 212개가 통과했다 (203 → 212).
  5. 서버에서 9가지를 확인했다. 결함 7가지를 넣는 확인을 했다. 7가지를 모두 잡았다.
  6. ADR-0003과 ADR-0005에 결론을 적었다. 작업 6의 설명 문서의 리뷰 메모 1에 한 줄을 더했다.
- **증상이 예상보다 넓었다**. 스텝 51은 "DB가 실패하면 401로 보인다고 예상한다"까지였다. 지금의 코드에서 실제로 일어나는 것이 있었다.

  | 요청 | 고치기 전 | 고친 뒤 |
  |---|---|---|
  | 경로에 `;`이 있다, 유효한 토큰 | 401 "액세스 토큰이 없거나 유효하지 않다", `instance`가 `/error` | 400, `instance`가 요청의 경로 |
  | 경로에 `//`이 있다, 유효한 토큰 | 401 | 400 |
  | 경로에 `%2e%2e`가 있다, 유효한 토큰 | 401 | 400 |
  | 필터의 안에서 예외가 난다 | 401, `instance`가 `/error` | 500 "서버에서 오류가 났다", `instance`가 요청의 경로 |
  | `/error`를 직접, 유효한 토큰 | 500, Spring Boot의 기본 본문 (`"status": 999`) | 404, Problem Details |
  | `/error`를 직접, 토큰이 없다 | 401 | 401 (그대로다. 맞다) |

  유효한 토큰을 가진 요청이 "토큰이 틀리다"는 답을 받고 있었다. Spring Security의 방화벽이 그런 경로를 거부하고 400을 `/error`로 넘긴다. 그 요청에 인증을 요구해서 401이 됐다.
- **원인**: `anyRequest().authenticated()`가 서버의 안에서 `/error`로 넘기는 요청에도 적용됐다. 그 요청에는 인증된 사람이 없다. Bearer 토큰의 필터는 넘긴 요청에서 다시 돌지 않는다.
- **고친 방법**
  - `SecurityConfig`: `dispatcherTypeMatchers(DispatcherType.ERROR).permitAll()`. 서버의 안에서 오류로 넘기는 요청만 허용한다. 경로(`/error`)를 허용한 것이 아니다. 클라이언트가 `/error`를 직접 부르면 여전히 인증이 필요하다.
  - `adapter.web`에 `ProblemDetailsErrorController`를 만들었다. 넘어온 상태와 원래의 경로로 Problem Details를 만든다. 글은 고정이다 (원인을 넣지 않는다). Spring Boot의 기본 오류 화면은 쓰이지 않는다.
- **더한 테스트** (9개. 고친 테스트 1개)

  | 테스트 | 무엇을 보는가 |
  |---|---|
  | `adr0005_a_path_that_the_server_does_not_accept_is_400_and_not_401` (3개) | `;`, `//`, `%2e%2e` + 유효한 토큰 → 400, `instance`가 `/error`가 아니다 |
  | `adr0005_…_is_400_without_a_token_too` | 토큰이 없어도 400 |
  | `adr0003_the_error_page_requested_directly_needs_an_access_token` | `/error`를 직접 → 401 |
  | `adr0005_the_error_page_requested_directly_with_a_token_is_problem_details` | 404, 기본 본문이 아니다 |
  | `ac3_3_an_expired_token_is_still_rejected` | 허용이 인증을 느슨하게 하지 않는다 |
  | `adr0005_an_unexpected_error_in_the_filter_is_500_and_not_401` | 유스케이스를 가짜로 바꿔서 예외를 만든다 |
  | `ac1_7_an_unexpected_error_in_the_filter_does_not_show_its_cause` | 원인이 본문에 없다 |
  | `ac3_5_a_valid_token_with_a_subject_that_is_not_a_member_is_rejected` (고쳤다) | 상태만이 아니고 본문도 본다. `instance`가 요청의 경로다 |

- **결함을 넣는 확인** (7가지를 모두 잡았다)

  | 넣은 결함 | 잡은 테스트 |
  |---|---|
  | 오류로 넘기는 요청을 허용하지 않는다 (고치기 전의 상태) | 수용 6 |
  | 숫자가 아닌 `sub`를 그대로 바꾼다 (스텝 49에서 수용 테스트가 놓쳤다) | 수용 1, 변환 1 |
  | 오류의 화면이 원인을 본문에 넣는다 | 수용 1 |
  | 오류의 화면이 `instance`를 정하지 않는다 | 수용 4 |
  | `/error`를 누구나 직접 부를 수 있다 | 수용 1 |
  | 오류가 없는 `/error`가 500이다 | 수용 1 |
  | 오류의 화면이 항상 500이다 | 수용 4 |

- **결정 (AI)**
  - 원인을 고쳤다. 증상 하나를 고치지 않았다. "필터의 안에서 예외를 잡는다"는 방화벽의 400을 고치지 못한다.
  - 오류의 화면은 웹 어댑터에 두었다. HTTP의 응답을 만드는 일이다. 보안 어댑터는 허용만 한다.
  - 오류의 화면의 글은 셋이다: 5xx는 "서버에서 오류가 났다", 404는 "요청한 자원이 없다", 나머지는 "요청을 받아들일 수 없다". 서버가 넘겨 준 메시지를 쓰지 않는다.
  - 테스트용 토큰을 만드는 코드를 `TestTokens`로 꺼냈다. 수용 테스트 3개가 함께 쓴다.
- **버린 대안**
  - 보안 어댑터에 필터를 더해서 예외를 잡고 500을 쓰는 것. 방화벽의 400은 그대로 401이다. 500의 본문을 만드는 코드가 두 어댑터에 생긴다.
  - `/error`의 경로를 모두에게 허용하는 것 (`requestMatchers("/error").permitAll()`). 한 줄이다. 누구나 오류의 화면을 직접 부른다.
  - 변환기가 모든 예외를 인증 실패로 바꾸는 것. 고장이 401로 보이는 것을 굳힌다.
- **문서 (AI가 승인된 문서를 고쳤다)**
  - ADR-0003: 오류로 넘기는 것에는 인증을 요구하지 않는다. `/error`를 직접 부르는 요청에는 요구한다.
  - ADR-0005: 실패의 표에 400(받아들이지 않는 경로). 컨트롤러에 닿지 않은 요청의 오류도 같은 형식이다. `instance`는 요청의 경로다. 500을 401로 응답해서는 안 된다.
- **고치지 않은 것**
  - 아주 긴 헤더(20000자)는 Tomcat이 HTML의 400으로 답한다. 서버의 앱에 닿기 전이다. Problem Details가 아니다.
  - 404의 글이 두 가지다: 컨트롤러의 404는 Spring의 영어("No static resource …")이고, 오류의 화면의 404는 한국어다.
- **관찰**
  - 이 결함은 작업 6의 테스트 203개와 결함을 넣는 확인 17가지를 모두 지나갔다. 찾은 순서: 결함을 넣는 확인에서 "수용 테스트가 하나를 놓쳤다"는 작은 이상이 나왔다 → 설명 문서를 쓰려고 이유를 확인했다 → 고치려고 넓게 봤더니 지금 일어나는 결함이 있었다. 세 단계 모두 "모른다"를 그대로 두지 않은 데서 나왔다.
  - 테스트가 상태(401)만 보면 틀린 이유의 401이 통과한다. 본문의 한 값(`instance`)이 이유를 구분했다. 작업 5의 R9와 반대의 방향이다: 거기서는 본문이 같아야 했고, 여기서는 본문이 달라야 했다.
  - 고친 코드는 한 줄과 클래스 하나다. 테스트는 9개다. 찾는 데 든 일이 고치는 일보다 컸다.
  - ADR-0005의 "오류의 본문은 반드시 Problem Details"는 스텝 44에서 MUST가 됐다. 그때 500(컨트롤러의 안)을 고쳤다. 컨트롤러의 밖의 오류는 그때 보지 않았다. MUST의 문장은 같았고, 대조한 범위가 좁았다.

## 스텝 56. 보안과 JWT를 배우는 게임

  1. `game-token-gatekeeper.html`을 만들었다. 파일 하나다. 외부 스크립트가 없다.

  | 막 | 역할 | 하는 일 | 배우는 것 |
  |---|---|---|---|
  | 1막 · 발급소 | 서버 | DB에 무엇을 저장할지 고른다. 토큰에 넣을 것을 고른다. 키로 서명한다 | 해시, base64url은 암호가 아니다, 서명 |

- **확인하지 않은 것 (미확정)**
  - 플러그인을 실제 세션에 올려서 스킬이 불리는 것. 매니페스트의 검사만 했다. 올리려면 새 세션이 필요하다.
  - playbook을 실제 작업에 쓴 적이 없다. 단계는 일지에서 뽑았다. 그러나 실행한 것은 아니다.
  - `t-reviewer`를 부른 적이 없다.
- **결정 (AI)**
  - **자율성을 pstack과 다르게 정했다.** pstack은 "되돌릴 수 있으면 진행한다"다. tstack은 "스텝의 안에서는 진행하고, 스텝의 사이에서는 멈춘다"다. 2026-11-16의 스텝 6이 근거다.
  - **principle은 독립 스킬이 아니고 라우터의 옆의 파일이다.** `like-pstack.md` 5.2의 권장이다.
  - **`t-mode`는 요청이 맞으면 저절로 불린다.** `like-pstack.md`의 틀은 `disable-model-invocation: true`다. 따르지 않았다. "작업 3을 한다"라고만 말해도 불리게 하려는 것이다. `t-reflect`는 직접 불러야 한다.
  - **감사 기록을 따로 두지 않았다.** pstack은 TSV를 쓴다. 이 프로젝트는 스텝마다 일지를 쓴다. 일지가 그 일을 한다.
  - **스텝 54의 열린 질문("구현이 승인된 문서를 고치는 것이 맞는가")에 기본값을 넣었다.** 결론을 더하는 일은 한다. 고친 곳마다 "확인이 필요하다"로 표시한다. 뜻을 바꾸는 일은 멈추고 묻는다. 보고마다 확인이 필요한 결정의 수를 적는다. 5개를 넘으면 **결정의 확인**을 권한다. 사용자가 정한 것이 아니다. 확인이 필요하다.
  - **스킬의 글을 한국어로 썼다.** `like-pstack.md`의 틀은 영어다. 이 프로젝트의 문서의 규칙을 따랐다. 규칙의 대상은 `docs/`의 아래다. `tstack/`은 그 밖이다. 넓게 읽었다.
  - **principle마다 "사례"에 일지의 스텝을 적었다.** 원칙이 어디에서 왔는지 보인다. 다른 프로젝트에서는 그 스텝을 볼 수 없다.
  - **`t-reviewer`를 넣었다.** 일지의 근거는 한 번이다 (스텝 54: 18개가 모두 "유지"다). 두 번의 규칙에 맞지 않는다. `like-pstack.md`의 "작성자는 판정자가 아니다"를 둘째 근거로 봤다.
  - **`.claude-plugin/marketplace.json`을 저장소의 루트에 두었다.** 이 저장소에서 플러그인을 설치하게 한다.
- **버린 대안**
  - pstack의 playbook의 목록(Bug fix, Refactoring, Perf issue 등)을 그대로 가져오는 것. 넓다. 이 프로젝트에서 반복된 유형이 아니다. `like-pstack.md` 5.5가 가져오지 말라고 한다.
  - RFC 2119로 다시 쓰는 일을 playbook으로 만드는 것. 두 번 했다 (스텝 42, 43). 그러나 tstack으로 시작한 프로젝트는 처음부터 그렇게 쓴다. reference(`doc-style.md`)와 검사(`keywords`)로 넣었다.
  - 학습용 게임의 playbook. 한 번 나왔다.
  - hook으로 일지를 강제하는 것 (커밋의 전에 `journal` 검사). 강제의 단계가 더 높다. 사용자의 설정을 바꾸는 일이다. 요청에 없다. 가이드에 넣지 않았다.
  - 플러그인을 `.claude/skills/`에 스킬로만 두는 것. 간단하다. 요청은 "플러그인"이다.
- **AI의 실수** (모두 실행해서 알았다)
  - `trace`의 정규식이 문장의 끝의 `R5.`를 놓쳤다. 첫 실행에서 "plan에 없다: R5, R7, R9, R10"이 나왔다. plan에는 있다. 문서가 아니고 측정이 틀렸다. 정규식을 고쳤다.
  - 결함을 넣는 실험의 스크립트가 둘째 실험부터 복사에 실패했다 (이미 스크래치 폴더의 안에 있었다). 결과가 모두 "미확정"으로 나왔다. 절대 경로로 고쳐서 다시 돌렸다.
- **관찰**
  - 일지가 스킬의 재료가 됐다. pstack의 `automate-me`는 대화의 기록에서 교정을 찾는다. 이 프로젝트는 스텝마다 "관찰"에 교정을 적었다. 교정을 찾는 일이 `grep`이 됐다. 일지를 쓴 값이 한 번 더 나왔다.
  - 교정과 확인된 방법 14개 중 principle이 된 것은 12개다. 나머지 2개는 단계(마무리의 1번과 6번)와 agent가 됐다. "`git add -A`를 쓰지 않는다"는 판단의 규칙이 아니고 절차다.
  - 검사 스크립트에도 "실패를 본 검사만 믿는다"를 적용했다. 첫 실행의 실패는 스크립트의 결함이었다. 검사를 믿기 전에 검사를 검사해야 했다.
  - `journal` 검사가 이 스텝에서 실제로 실패했다. 그 검사가 막으려는 것(2026-11-16의 스텝 8, 9를 일지에서 뺀 일)과 같은 상태였다.
  - tstack은 아직 한 번도 쓰이지 않았다. `like-pstack.md`의 말로는 "실행하지 않은 스킬은 초안이다". 다음 작업(plan의 작업 7)이 첫 사용이 될 수 있다.
