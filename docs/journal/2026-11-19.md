## 스텝 82. push, 질문, 그리고 git을 막는 hook

- **요청 1**: push.
- **한 일**: 커밋 2개(`f329b7a`, `db38f7e`)를 push했다. HEAD가 `main`에 있는 것을 먼저 확인했다.
- **질문 (사용자)**: "리뷰에서 배운 것"을 더 강한 규칙으로 만들어서 적용하는 방법이 있는가?
- **답 (AI)**: 규칙의 힘은 4층이다: 글(`CLAUDE.md`), 절차(playbook, 리뷰어), 검사(테스트, CI), 차단(hook). 14항목은 모두 1층에 있다. 13번은 4층으로, 1, 2, 3, 6번은 mutation testing으로 3층으로 올릴 수 있다. 8, 9, 10번은 판단이라서 2층이 한계다. 권장 3개: git을 막는 hook, PIT, CI.
- **요청 2**: 3개를 모두 한다. 커밋을 따로 한다. 이 스텝은 첫 번째(hook)다.
- **한 일**
  1. `.claude/hooks/guard-git-discard.py`를 썼다. Claude Code의 `PreToolUse` hook이다. 작업 트리에 커밋하지 않은 변경이 있을 때 그 변경을 지우는 git 명령을 막는다.
  2. `.claude/settings.json`을 만들고 hook을 연결했다.
  3. 명령 26개를 스크립트에 넣어서 판정을 봤다. 모두 예상과 같다 (막음 12, 통과 14).
- **결정** (AI가 정했다)
  - 작업 트리가 깨끗하면 아무것도 막지 않는다. 지울 변경이 없다.
  - 가지를 바꾸는 `git checkout main`은 막지 않는다. git이 스스로 변경을 지킨다.
  - `git stash`를 막는다. 변경을 지우지는 않는다. `CLAUDE.md`의 13번이 stash를 적었다. stash의 뒤에 pop을 잊으면 변경이 보이지 않게 된다. `list`, `show`, `pop`, `apply`는 통과한다.
  - 설정은 `.claude/settings.json`(저장소에 넣는다)에 뒀다. 이 저장소에서 Claude Code를 쓰는 모두에게 적용된다.
  - 스크립트는 Python이다. 따옴표의 안의 글(`echo "git checkout -- x"`, 커밋의 메시지)을 명령으로 읽지 않으려면 셸의 문법으로 나눠야 한다.
- **버린 대안**
  - `permissions.deny`의 규칙으로 막는 것. 설정 1줄이다. 작업 트리가 깨끗할 때도 막는다. 조건을 넣지 못한다.
  - git의 hook(`pre-commit` 등). 사람에게도 적용된다. `checkout`과 `restore`의 앞에 도는 git hook은 없다.
- **한계**: 스크립트는 명령을 글자로 읽는다. 변수, 별칭, 스크립트 파일의 안의 git은 보지 못한다. 사람이 터미널에서 치는 명령에는 적용되지 않는다.
- **검증**

  | 확인한 것 | 방법 | 판정 | 증거 |
  |---|---|---|---|
  | 판정 | 명령 26개를 스크립트에 넣음 | 확인됨 | 막음 12, 통과 14. 예상과 같다 |
  | 설정의 모양 | `jq`로 hook의 명령을 읽음 | 확인됨 | 명령이 나온다 |
  | 실제로 걸리는가 | 더러운 작업 트리에서 `git checkout -- CLAUDE.md`를 실행 | 확인됨 | "PreToolUse:Bash hook error: 막았다"가 나왔다. 명령은 실행되지 않았다 |

- **관찰**: 스텝 78의 실수는 Claude Code의 권한의 검사가 막았다. 그 검사는 이 프로젝트의 규칙이 아니다. 이제 같은 명령을 프로젝트의 hook이 막는다. 규칙이 사람의 설정에서 저장소로 옮겨졌다.

## 스텝 83. mutation testing (PIT)

- **요청**: 스텝 82의 요청의 두 번째.
- **한 일**
  1. 버전을 저장소의 메타데이터에서 확인했다: `info.solidsoft.pitest` 1.19.0, PIT 1.30.2, `pitest-junit5-plugin` 1.2.3. Gradle 9.9.1, Java 25, JUnit 6.0.3에서 돈다.
  2. `build.gradle.kts`에 PIT를 더했다. 대상은 `trealworld.domain`과 `trealworld.application`이다.
  3. 처음 실행: 결함 63개 중 56개를 잡았다 (89%). 7개가 남았다.
  4. 7개를 고쳤다 (아래의 표). 다시 실행: 61개 중 61개 (100%).
  5. 기준을 100으로 정했다. `check`가 `pitest`를 부른다. `./gradlew build`가 함께 돌린다.
  6. ADR-0004와 `CLAUDE.md`에 적었다.
- **남은 7개와 처리**

  | 결함 | 뜻 | 처리 |
  |---|---|---|
  | `RegisterMemberService`: 저장의 앞의 중복 확인을 지움 | 지워도 테스트가 통과했다. 저장이 실패하면 다시 확인하기 때문이다. 앞의 확인의 값("해시를 만들기 전에 거부한다")을 보는 테스트가 없었다 | 테스트를 더했다: 중복이면 해시를 만들지 않는다 |
  | `Password.toString()`이 빈 글을 돌려줌 | 단언이 "비밀번호가 없다"였다. 빈 글도 통과한다 | 단언을 "같다"로 바꿨다 |
  | `PasswordHash.toString()`이 빈 글을 돌려줌 | 위와 같다. **오늘 스텝 78에서 쓴 테스트다** | 위와 같다 |
  | `AccessToken`, `RegisterMemberCommand`, `LoginCommand`의 `toString()` (3개) | 테스트가 없었다. 비밀번호와 토큰을 가리는 코드다 | `TextOfSecretsTests`를 더했다 |
  | `Email`: `length() > 508`을 `>=`로 바꿈 | 죽일 수 없다 (동치). 508 char인 입력은 항상 254자를 넘는다. 뒤의 검사가 어차피 거부한다 | 그 검사를 지웠다. 뒤의 검사와 같은 일을 했다 |

- **검증**

  | 확인한 것 | 방법 | 판정 | 증거 |
  |---|---|---|---|
  | PIT가 돈다 | `./gradlew pitest` | 확인됨 | 61 / 61. 약 3초 |
  | 기준이 빌드를 깬다 | `PasswordHashTests`의 단언을 약하게 되돌리고 `./gradlew build` | 확인됨 | "Mutation score of 98 is below threshold of 100". 빌드 실패. 테스트는 복사한 것으로 되돌렸다 |
  | 전체 | `./gradlew clean build` | 확인됨 | 247개, 실패 0. PIT 포함 |

- **결정** (AI가 정했다)
  - 대상을 `domain`과 `application`으로 했다. Spring 없이 도는 테스트가 있는 곳이다. 어댑터와 수용 테스트는 뺐다. 결함마다 서버를 다시 띄우면 느리다.
  - 기준은 100이다. 지금 100이다. 낮은 기준은 "몇 개는 놓쳐도 된다"가 된다. 어느 것을 놓쳐도 되는지 정할 근거가 없다.
  - `build`에 묶었다. 따로 실행하는 검사는 잊는다. 3초다.
  - 동치인 결함은 코드를 지워서 없앴다. 그 검사는 "긴 입력을 소문자로 바꾸지 않는다"는 최적화였다 (스텝 78). 뒤의 검사가 같은 입력을 거부한다. 본문의 크기는 받아들인 한계다 (스텝 79).
- **버린 대안**
  - 보안 어댑터의 단위 테스트(디코더, 발급, 키)도 대상에 넣는 것. Spring 없이 돈다. BCrypt의 테스트가 결함마다 다시 돈다. 다음에 따로 본다.
  - 기준을 89로 정하고 천천히 올리는 것. 지금의 7개를 그대로 둔다.
- **관찰**
  - 스텝 78에서 쓴 테스트 1개가 약했다 (`PasswordHash.toString()`). 같은 날에 쓴 `CLAUDE.md`의 4번("단언은 기대하는 값으로 쓴다")을 어긴 테스트다. 규칙을 글로 쓴 것만으로는 지켜지지 않았다. 도구가 2초 만에 찾았다.
  - `RegisterMemberService`의 결함은 codex의 리뷰도 찾지 못했다. "앞의 확인은 왜 있는가"를 테스트가 말하지 않았다. 코드의 주석에도 없었다.
  - 스텝 78에서 한 추정("PIT는 재시작 테스트의 약점을 찾지 못한다")은 확인하지 못했다. 수용 테스트는 대상이 아니다.

## 스텝 84. 스텝 83의 실수: 실패한 검사를 보지 않고 커밋함

- **무엇**: 스텝 83의 커밋(`d6d98db`)의 앞에 `tstack-check.py keywords`가 **실패**했다. AI는 출력의 마지막 줄(수의 요약)만 봤다. 실패의 줄은 그 위에 있었다. 실패한 채로 커밋했다.
- **원인의 문장**: ADR-0004에 AI가 쓴 "죽일 수 없는 결함". 검사는 허용의 뜻이 아닌 "수 없다"를 막는다 (`doc-style.md`).
- **한 일**: 문장을 "어떤 테스트로도 잡지 못하는 결함"으로 고쳤다. 같은 줄의 "모두 잡아야 한다"에 키워드의 굵은 글씨를 넣었다. 검사 2개를 다시 돌리고 끝의 코드를 봤다: `keywords` 0, `trace` 0.
- **찾은 방법**: 다음 스텝(CI)을 준비하면서 같은 검사를 다시 돌렸다. 이번에는 출력의 앞을 봤다.
- **결정** (AI가 정했다): 커밋을 고쳐 쓰지 않았다 (`--amend`). 따로 커밋했다. 실수가 기록에 남는다.
- **관찰**
  - 검사가 있어도 결과를 읽지 않으면 없는 것과 같다. `| tail -1`이 실패를 가렸다. 검사의 판정은 끝의 코드다. 글이 아니다.
  - 이 실수는 다음 스텝의 이유다. CI는 끝의 코드를 본다. 사람과 AI가 출력을 읽는 것에 기대지 않는다.
  - `CLAUDE.md`의 "리뷰에서 배운 것"에 1줄을 더할 만하다: 검사의 통과는 끝의 코드로 확인한다. 더하지 않았다. CI가 같은 일을 한다. 사용자가 정한다.
