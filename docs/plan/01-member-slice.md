# Plan 01. 회원 슬라이스

- 상태: 승인 (2026-11-16). 수정 (2026-11-17): 더한 수용 기준 3개를 반영했다. 수정 (2026-11-17, 작업 2의 검토): 작업 3, 4에 `allowEmptyShould`를 지우는 일을 더했다. 수정 (2026-11-17): AC-1.9를 반영했다. 구현은 사용자의 지시가 있을 때 시작한다. 구현과 검증이 끝났다 (2026-11-18, 일지의 스텝 72와 75). 끝의 조건 4개가 모두 찼다. 사용자의 종료 확인을 기다린다. 수정 (2026-11-19, 일지의 스텝 78): 이 줄에 지금의 상태를 적었다. 수정 (2026-11-19, 일지의 스텝 79): 읽는 법을 더했다.
- 읽는 법: 이 plan은 RFC 2119의 키워드를 쓰지 않는다. 문체의 규칙(`CLAUDE.md`의 "문서의 문체", 2026-11-18)보다 먼저 썼다. 끝난 plan이라서 다시 쓰지 않는다. 다음 plan부터 규칙을 따른다. 이 plan의 "방식"과 "끝의 조건"의 문장은 모두 꼭 지키는 것이다.
- 입력: [Spec 01](../spec/01-member-signup-login.md), [Domain 01](../domain/01-member.md), [ADR](../adr/) 0001~0005

## 방식

- 모든 작업은 테스트 먼저다 ([ADR-0004](../adr/0004-verification-tdd.md)). 실패하는 테스트 → 구현 → 통과 → 정리.
- 작업 하나가 끝나면 전체 테스트를 돌리고, 일지를 쓰고, 커밋한다.
- 작업 하나는 사용자의 확인을 받은 뒤에 다음으로 간다.

## 작업 순서

| # | 작업 | 검증할 내용 |
|---|---|---|
| 1 | 프로젝트 뼈대를 만든다. Spring Boot의 버전을 확인해서 ADR-0001에 적는다. | 빌드가 성공한다. 빈 애플리케이션이 뜬다. |
| 2 | 아키텍처 테스트를 쓴다. 패키지 `domain`, `application`, `adapter`를 만든다. | ADR-0002의 규칙 1~5가 테스트로 있다. 규칙을 일부러 어기면 테스트가 실패한다. |
| 3 | 도메인을 만든다: 회원, 이메일, 사용자 이름, 비밀번호 해시. | R1, R2, R3, R5. Spring 없이 테스트가 돈다. 아키텍처 테스트의 규칙 1, 3에서 `allowEmptyShould`를 지운다. |
| 4 | 가입을 만든다 (목표 1). | AC-1.1 ~ AC-1.9. R4, R6, R7. 저장된 값이 비밀번호의 원문이 아니다. 응답에 비밀번호 해시가 없다. 아키텍처 테스트의 규칙 2, 4, 5에서 `allowEmptyShould`를 지운다. |
| 5 | 로그인을 만든다 (목표 2). | AC-2.1 ~ AC-2.5. R8, R9. 없는 이메일과 틀린 비밀번호의 응답이 같다. |
| 6 | 내 정보 조회를 만든다 (목표 3). | AC-3.1 ~ AC-3.5. R10. 만료된 토큰과 위조된 토큰을 거부한다. 401의 본문이 ADR-0005의 오류 형식이다. |
| 7 | 전체 흐름을 확인한다. | 가입 → 로그인 → 조회가 테스트 하나로 이어진다. 모든 AC와 R에 테스트가 있다. 아키텍처 테스트가 통과한다. |

## 작업 4~6의 안쪽 순서

각 목표는 같은 순서로 만든다.

1. 수용 테스트를 쓴다. 실패한다.
2. 필요한 도메인 규칙의 단위 테스트를 쓰고, 도메인을 고친다.
3. 유스케이스와 포트를 만든다.
4. 나가는 어댑터를 만든다 (영속성, 보안).
5. 웹 어댑터를 만든다. 수용 테스트가 통과한다.
6. 정리한다. 아키텍처 테스트가 통과한다.
