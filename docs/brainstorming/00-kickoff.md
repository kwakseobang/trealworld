# 00. 킥오프 브레인스토밍

- 작성일: 2026-11-16
- 상태: 초안 (대화하면서 계속 고친다)
- 입력 자료: RealWorld 스펙 허브
  - 저장소: <https://github.com/realworld-apps/realworld>
  - 읽은 버전: 커밋 `2558884` (2026-11-02). 이 문서의 숫자(926줄, 19개)는 이 버전의 것이다.
  - 아래의 경로(`specs/api/...`)는 이 저장소 안의 경로다.

## 1. 내가 이해한 의도

API 스펙을 그대로 구현하지 않는다.
스펙을 "결과물"로 보고, 그 뒤에 있는 **개발 의도**를 먼저 복원한다.
그 다음 순서로 문서를 만든다.

```
API spec (입력)
  → 의도 추출 + 브레인스토밍   ← 지금 여기
  → spec (우리가 다시 쓴 요구사항)
  → domain (도메인 모델, 용어집)
  → ADR (설계 결정 기록)
  → plan (구현 계획)
  → 개발
```

진행 방식: 한 번에 하나만 한다. 각 단계는 대화로 확인한 뒤에 다음으로 간다.

## 2. 입력 자료에서 본 것

| 자료 | 위치 | 성격 |
|---|---|---|
| OpenAPI | `specs/api/openapi.yml` (926줄) | **무엇**을 주고받는지 |
| Hurl 테스트 | `specs/api/hurl/` | **어떻게 동작해야** 하는지 (정답 기준) |
| E2E 테스트 | `specs/e2e/*.spec.ts` | 사용자 시나리오 (프론트엔드 기준) |
| 문서 사이트 | `docs/` | 사람이 쓴 설명 |

엔드포인트는 19개다. 묶으면 6개 주제가 된다.

- 인증/회원: 가입, 로그인, 내 정보 조회/수정
- 프로필: 조회, 팔로우/언팔로우
- 글(Article): 목록, 피드, 작성, 조회, 수정, 삭제
- 댓글: 목록, 작성, 삭제
- 좋아요(Favorite): 추가, 취소
- 태그: 목록

## 3. 스펙에서 읽히는 의도 (가설)

아직 검증하지 않은 추측이다. 다음 단계에서 하나씩 확인한다.

1. **"Medium 같은 소셜 블로그"** 가 제품의 정체다. 핵심 가치는 "글을 쓰고, 사람을 따라가고, 반응한다"이다.
2. **읽기는 열려 있고, 쓰기는 닫혀 있다.** 글/프로필/태그 조회는 로그인 없이 된다. 변경은 모두 인증이 필요하다.
3. **"나"의 관점이 응답에 섞인다.** `following`, `favorited` 는 같은 자원이라도 보는 사람에 따라 값이 다르다. 조회 모델이 "누가 보는가"에 의존한다.
4. **소유권이 권한 규칙의 전부다.** 관리자 역할이 없다. "내 글, 내 댓글만 고치고 지운다"가 유일한 규칙으로 보인다.
5. **피드와 전체 목록은 다른 개념이다.** `/articles/feed` 는 팔로우 관계에서 나오는 개인화된 뷰다.
6. **slug 는 글의 공개 식별자다.** 제목에서 만든다. 제목이 바뀌면 slug 가 어떻게 되는지가 숨은 규칙이다.
7. **태그는 독립 자원이 아니다.** 만들기/지우기 API가 없다. 글에 붙으면서 생긴다.

## 4. 스펙이 말해주지 않는 것 (빈칸)

API 스펙은 "모양"만 말한다. 아래는 우리가 결정해야 한다.

- 불변식: 자기 자신을 팔로우할 수 있는가? 같은 글에 좋아요를 두 번 누르면?
- 삭제의 영향: 글을 지우면 댓글과 좋아요는?
- 유일성: username, email, slug 충돌 처리
- 비기능 요구: 성능, 보안 수준, 페이지네이션 한계
- 기술 선택: 언어, 프레임워크, DB, 아키텍처 스타일

이 빈칸들이 나중에 **ADR 후보**가 된다.

## 5. 내 아이디어

- **A. 의도는 OpenAPI보다 테스트에 더 많다.** Hurl 테스트는 엣지 케이스와 에러 규칙을 담고 있다. 의도 추출의 1차 자료로 Hurl 을 쓰는 것을 권장한다.
- **B. 엔드포인트 단위가 아니라 "사용자 목표" 단위로 추출한다.** 예: "POST /articles" 대신 "작가가 글을 발행한다". 이렇게 하면 spec 이 API 모양에 묶이지 않는다.
- **C. 의도마다 근거를 붙인다.** 각 의도에 "스펙의 어느 부분에서 읽었는가"를 적는다. 추측과 사실을 구분한다.
- ~~**D. 원본 스펙은 마지막에 검증 도구로 다시 쓴다.** 개발이 끝나면 Hurl 테스트를 돌린다. 우리가 추출한 의도가 맞았는지 확인하는 수용 테스트가 된다.~~ → 6.6의 결정으로 폐기
- **E. 문서는 작게, 번호를 붙여 쌓는다.** `docs/brainstorming/`, `docs/spec/`, `docs/domain/`, `docs/adr/`, `docs/plan/`. 한 문서는 한 주제만 다룬다. (이후 6.2의 결정으로 `docs/journal/`이 추가됐다.)
- **F. 첫 번째 수직 슬라이스는 작게 잡는다.** 후보: "가입 → 로그인 → 내 정보 조회". 전체 흐름(spec→domain→ADR→plan→코드)을 한 번 끝까지 돌려본다.

## 6. 결정된 것

### 6.1 프로젝트의 목적 (2026-11-16)

- 목적은 **방법론 실험**이다. "스펙 → 의도 → 문서 → 개발" 흐름을 검증한다.
- 이 과정을 **세미나에서 사례로 발표한다.**
- 예제(RealWorld) 자체는 중요하지 않다. **어떤 process로 작업했는지**가 중요하다.

이 결정에서 나오는 결과:

- 산출물은 두 종류다. (1) 프로젝트 문서와 코드, (2) **과정의 기록**. 발표에는 (2)가 더 중요하다.
- 각 단계에서 "무엇을 만들었는가"와 함께 "왜 이 순서로, 어떻게 결정했는가"를 남긴다.
- 예제의 완성도는 낮춰도 된다. 전체 기능을 다 구현할 필요가 없을 수 있다.
- 과정은 다른 프로젝트에 다시 쓸 수 있어야 한다. RealWorld에만 맞는 방법은 피한다.

### 6.2 과정의 기록 방식 (2026-11-16)

- **별도 작업 일지**로 남긴다. 위치: `docs/journal/`.
- 날짜별 파일 하나. 스텝마다 요청/질문, 답, 한 일, 결정, 버린 대안, 관찰을 쓴다.
- 프로젝트 문서에는 결론만 쓴다. 과정은 일지에 쓴다.

### 6.3 구현 범위 (2026-11-16)

- 목표는 **수직 슬라이스 1~2개**다. 전체 19개 엔드포인트를 구현하지 않는다.
- 어떤 슬라이스를 고를지 → 6.8에서 결정

### 6.4 진행 규칙 (2026-11-16)

- 지금은 브레인스토밍 단계다. **구현을 시작하지 않는다.**
- 사용자의 지시에 따라 한 스텝씩 진행한다. AI가 앞서가지 않는다.

### 6.5 범위: 백엔드만 (2026-11-16)

- 백엔드(API 서버)만 만든다. 프론트엔드는 만들지 않는다.

### 6.6 원본과의 호환 (2026-11-16)

- 원본 스펙과의 호환은 **중요하지 않다.** 원본에서는 **아이디어만** 가져온다.
- API의 모양(경로, 필드 이름, 응답 구조)은 우리가 다시 정할 수 있다.
- 영향: 5절의 아이디어 D("원본 Hurl 테스트를 마지막 수용 테스트로 쓴다")는 **더 이상 맞지 않는다.** Hurl 테스트는 의도를 읽는 자료로만 쓴다. 검증 방법은 나중에 다시 정한다.

### 6.7 기술 스택 (2026-11-16)

사용자가 정했다.

| 항목 | 선택 |
|---|---|
| 프레임워크 | Spring Boot 최신 버전 |
| 언어 | Java 25 |
| 빌드 | Gradle Kotlin DSL (`build.gradle.kts`) |
| 영속성 | JPA |
| DB | H2 |
| 보조 도구 | Lombok |
| 테스트 | JUnit, ArchUnit |

- ArchUnit이 들어 있다. 아키텍처 규칙을 테스트로 강제한다는 뜻이다. 어떤 규칙인지는 아직 정하지 않았다.

### 6.8 첫 번째 슬라이스 (2026-11-16)

- **가입 → 로그인 → 회원 정보 조회**
