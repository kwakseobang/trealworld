설계 문서 8개 뒤의 첫 코드: 빈 Spring Boot 4 애플리케이션

독자 가정. Spring과 Gradle을 잘 아는 독자다. Spring Boot의 기본 설명은 뺐다. Spring Boot 4에서 바뀐 것과, 이 커밋에서 AI가 정한 것에 집중했다.

1. 먼저 알아야 할 것

이 커밋의 앞: 코드가 0줄이었다

저장소에는 문서만 있었다. 커밋 4개, 설계 문서 8개(spec 1, domain 1, ADR 5, plan 1)다. 이 커밋은 plan 01의 작업 1이다. plan은 작업 1에 두 가지만 요구한다.

plan의 요구뜻
빌드가 성공한다./gradlew build가 끝까지 간다
빈 애플리케이션이 뜬다기능이 없는 서버가 시작한다

ADR-0001에는 숙제가 하나 있었다: "Spring Boot의 버전 번호는 프로젝트를 만들 때 확인해서 이 문서에 적는다."

Spring Boot 4에서 바뀐 것 3개

이 커밋의 빌드 파일을 읽으려면 이 3개가 필요하다. Spring Boot 3의 기억으로 읽으면 낯설다.

무엇Boot 3Boot 4 (이 커밋)
웹 스타터spring-boot-starter-webspring-boot-starter-webmvc
테스트 스타터spring-boot-starter-test 하나기술마다 하나: -webmvc-test, -data-jpa-test
따라오는 버전Spring 6, Jackson 2, JUnit 5Spring 7, Jackson 3, JUnit 6
테스트 스타터가 왜 나뉘었는가

Spring Boot 4는 자동 설정을 기술마다 작은 모듈로 쪼갰다. 테스트 지원도 같이 쪼개졌다. 예를 들어 MockMvc의 테스트 지원은 spring-boot-webmvc-test에 있다. @DataJpaTest는 spring-boot-data-jpa-test에 있다. 두 스타터가 모두 spring-boot-starter-test(JUnit, AssertJ, Mockito)를 끌어온다. 그래서 빌드 파일에 spring-boot-starter-test가 직접 보이지 않는다.

문제는 이것이다: 승인된 문서는 "Spring Boot 최신 안정 버전"이라고만 말한다. 코드는 숫자가 필요하다.

2. 핵심 아이디어

숫자 3개만 직접 고른다. 나머지 버전은 모두 그 숫자를 따라오게 한다. 그리고 아직 쓰지 않는 것은 넣지 않는다.

직접 고른 숫자는 Spring Boot 4.1.2, Java 25, Gradle 9.9.1이다. Spring, Hibernate, Tomcat, H2, Lombok, JUnit의 버전은 빌드 파일에 없다. Spring Boot가 정한다. 의존성도 최소다. ADR-0001의 스택에서 지금 필요한 4개만 있다. Spring Security(ADR-0003), 검증, ArchUnit(ADR-0002)은 처음 쓰는 작업에서 더한다. 그러면 "이 의존성은 왜 들어왔는가"의 답이 커밋 역사에 남는다.

3. 변경을 순서대로 읽기

스텝 1 — 버전 3개를 고정한다

왜: "최신 안정 버전"은 날마다 뜻이 바뀐다. 숫자로 바꿔야 누구의 컴퓨터에서나 같은 빌드가 된다.

build.gradle.kts — 빌드의 정의다. 이 프로젝트에서 사람이 읽을 가치가 가장 큰 파일이다.

plugins {    java    id("org.springframework.boot") version "4.1.2"    id("io.spring.dependency-management") version "1.1.7"} group = "trealworld"version = "0.0.1-SNAPSHOT" java {    toolchain {        languageVersion = JavaLanguageVersion.of(25)    }} repositories {    mavenCentral()

볼 곳:

  • version "4.1.2" — Spring Initializr의 기본값이다. 같은 날 4.2.0은 RC2였다. RC와 SNAPSHOT은 "안정"이 아니므로 뺐다.
  • io.spring.dependency-management — "따라오는 버전"을 만드는 플러그인이다. 이 플러그인 때문에 아래 의존성에 버전 번호가 없다.
  • toolchain — Gradle을 실행하는 JDK와 코드를 컴파일하는 JDK를 나눈다. 컴파일은 항상 25로 한다.
  • group = "trealworld" — AI가 정했다. Initializr의 기본값은 com.example이다.

gradle/wrapper/gradle-wrapper.properties — ./gradlew가 내려받을 Gradle의 버전을 정한다.

distributionUrl=https\://services.gradle.org/distributions/gradle-9.9.1-bin.zip

이 컴퓨터에 설치된 Gradle은 9.7.0이다. 빌드는 그것을 쓰지 않는다. wrapper가 9.9.1을 받아서 쓴다.

도구의 버전이 정해졌다. 다음은 "무엇을 넣는가"다.

스텝 2 — 지금 쓰는 의존성만 넣는다

왜: plan의 요구는 "빈 애플리케이션이 뜬다"다. 그것에 필요한 것과 ADR-0001의 스택만 있으면 된다.

build.gradle.kts (이어서)

 dependencies {    implementation("org.springframework.boot:spring-boot-starter-data-jpa")    implementation("org.springframework.boot:spring-boot-starter-webmvc")    compileOnly("org.projectlombok:lombok")    runtimeOnly("com.h2database:h2")    annotationProcessor("org.projectlombok:lombok")    testImplementation("org.springframework.boot:spring-boot-starter-data-jpa-test")    testImplementation("org.springframework.boot:spring-boot-starter-webmvc-test")    testCompileOnly("org.projectlombok:lombok")    testRuntimeOnly("org.junit.platform:junit-platform-launcher")    testAnnotationProcessor("org.projectlombok:lombok")} tasks.withType<Test> {    useJUnitPlatform()}
ADR-0001의 항목의존성상태
Spring Boot (웹)starter-webmvc있다
JPAstarter-data-jpa있다
H2com.h2database:h2 (runtimeOnly)있다
LombokcompileOnly + annotationProcessor있다. 아직 쓰는 코드는 없다
JUnit테스트 스타터 2개가 끌어온다있다 (6.0.3)
ArchUnit—없다. 작업 2에서 더한다

볼 곳:

  • Lombok이 4줄이다. compileOnly는 "컴파일할 때만 보인다"이고, annotationProcessor는 "컴파일할 때 코드를 만든다"다. jar에는 들어가지 않는다. 테스트 코드용으로 같은 2줄이 한 번 더 있다.
  • junit-platform-launcher — Gradle이 JUnit을 실행할 때 필요하다. Gradle 9는 이것을 자동으로 넣지 않는다.
  • 없는 줄: Initializr는 H2를 고르면 spring-boot-h2console도 넣는다. AI가 그 줄을 지웠다. 요청한 적이 없기 때문이다.

빌드가 정의됐다. 이제 빌드할 코드가 필요하다.

스텝 3 — 뜨는 것 하나와, 뜨는지 확인하는 것 하나

왜: "빈 애플리케이션이 뜬다"를 사람이 눈으로 한 번 확인하면 다음 사람은 모른다. 테스트로 남기면 빌드할 때마다 확인된다.

src/main/java/trealworld/TrealworldApplication.java — 시작점이다. 컴포넌트 스캔의 뿌리도 여기다.

package trealworld; import org.springframework.boot.SpringApplication;import org.springframework.boot.autoconfigure.SpringBootApplication; @SpringBootApplicationpublic class TrealworldApplication {     public static void main(String[] args) {        SpringApplication.run(TrealworldApplication.class, args);    } }

패키지가 trealworld 한 단어다. ADR-0002의 패키지는 이 아래에 생긴다: trealworld.domain, trealworld.application, trealworld.adapter. 이 클래스는 세 패키지의 밖(뿌리)에 있다. 작업 2의 ArchUnit 규칙은 이 클래스를 어느 쪽에도 넣지 않아야 한다.

src/test/java/trealworld/TrealworldApplicationTests.java — 전체 컨텍스트가 뜨는지 확인한다.

@SpringBootTestclass TrealworldApplicationTests {     @Test    void contextLoads() {    } }

테스트의 본문이 비어 있다. 틀린 것이 아니다. @SpringBootTest가 컨텍스트를 띄우다가 실패하면 테스트가 실패한다. 실제로 이 테스트는 Hibernate와 H2의 연결까지 띄운다.

src/main/resources/application.properties, settings.gradle.kts — 이름만 있다.

spring.application.name=trealworld
rootProject.name = "trealworld"

설정이 1줄이다. DB의 주소도, 포트도 없다. H2가 classpath에 있으면 Spring Boot가 인메모리 DB를 만든다. 실제로 뜬 주소는 jdbc:h2:mem:a02c5c20-…처럼 무작위다.

코드가 뜬다. 남은 것은 문서의 숙제다.

5. 리뷰 메모

"확인"은 실행해서 본 것이다. "추정"은 파일을 읽고 판단한 것이다.

  • [확인] spring.jpa.open-in-view 경고가 뜬다. 시작할 때의 로그에 WARN … spring.jpa.open-in-view is enabled by default가 있다. 기본값은 "HTTP 요청이 끝날 때까지 영속성 컨텍스트를 연다"다. ADR-0002(헥사고날)와 ADR-0005(응답용 객체)의 방향과 반대다. 웹 어댑터가 지연 로딩을 건드려도 오류가 나지 않아서, 경계를 넘는 실수가 숨는다. → false로 끄는 것을 권장한다. 시점은 지금이거나 JPA를 처음 쓰는 작업 4다.
  • [확인] 8080 포트가 이미 쓰이고 있다. 검증할 때 이 컴퓨터의 8080에 다른 Java 프로세스가 있었다. 그래서 18080에서 띄웠다. [추정] 같은 상태에서 ./gradlew bootRun을 그대로 실행하면 포트 충돌로 실패한다. 세미나의 시연 전에 확인이 필요하다. 테스트는 영향이 없다 (@SpringBootTest의 기본값은 실제 포트를 열지 않는다).
  • [확인] Lombok은 아직 검증되지 않았다. 빌드는 성공했다. 그러나 Lombok 애너테이션을 쓰는 코드가 0줄이다. "Lombok 1.18.48이 Java 25에서 동작한다"는 작업 3(도메인)에서 처음 확인된다.
  • [확인] Jackson이 3이다 (3.1.7). 패키지가 com.fasterxml.jackson에서 tools.jackson으로 바뀌었다. 작업 4에서 JSON을 직접 다루는 코드를 쓰면, 기억에 있는 Jackson 2의 import는 컴파일되지 않는다.
  • [확인] JUnit이 6이다 (6.0.3). ADR-0001은 "JUnit"이라고만 적었다. 틀리지 않다. 버전을 적을지는 사용자가 정한다.
  • [추정] JDK 25가 없는 컴퓨터에서는 빌드가 실패한다. settings.gradle.kts에 toolchain을 자동으로 내려받는 플러그인(foojay resolver)이 없다. 이 컴퓨터에는 Temurin 25.0.4가 있어서 문제가 없다. 발표를 본 사람이 저장소를 받아서 돌릴 때의 문제다.
  • [확인] DB를 눈으로 볼 방법이 없다. H2 콘솔을 뺐고, DB의 이름은 무작위다. plan의 작업 4는 "저장된 값이 비밀번호의 원문이 아니다"를 테스트로 검증하므로 필요하지 않다. 시연에서 DB를 보여주려면 콘솔을 다시 넣어야 한다.
  • [질문] 패키지 이름 trealworld. 한 단어다. 관례(com.example.…)와 다르다. 배포하지 않으므로 문제는 없다. 바꾸려면 작업 2의 전이 가장 싸다. 작업 2부터 ArchUnit 규칙이 이 이름을 쓴다.
  • [질문] contextLoads에는 AC/R의 ID가 없다. ADR-0004는 테스트 이름에 ID를 넣는다. 이 테스트는 어느 수용 기준도 검증하지 않는다. "뼈대의 테스트는 예외"라고 적을지, 작업 7에서 전체 흐름 테스트로 바꿀지 정해야 한다.

6. 이해했는지 확인하기

점수를 매기는 시험이 아니다. 아직 이해하지 못한 곳을 찾는 도구다. 권장하는 규칙: 통과하기 전에는 이 변경의 리뷰를 요청하지 않는다.

  1. 내일 Spring Boot 4.1.3이 나온다. 이 저장소를 새로 받아서 ./gradlew build를 실행하면 Hibernate의 버전은 어떻게 되는가?

    빌드 파일에 숫자로 고정한 것은 Spring Boot 4.1.2다. 의존성에 버전이 없는 것은 "최신을 받는다"가 아니다. "Spring Boot가 정한 버전을 따른다"다. Spring Boot의 숫자를 사람이 바꾸기 전에는 아무것도 바뀌지 않는다.

    다시 읽기: 스텝 1

  2. 빌드가 성공했고 테스트도 통과했다. 이 사실은 "Lombok이 Java 25에서 동작한다"에 대해 무엇을 말하는가?

    검증은 실제로 실행된 것만 증명한다. 이 커밋의 Java 코드 2개에는 Lombok 애너테이션이 없다. Lombok은 classpath에 있을 뿐이고, 만든 코드가 0줄이다. 첫 확인은 작업 3(도메인)에서 일어난다.

    다시 읽기: 리뷰 메모

  3. build.gradle.kts에서 runtimeOnly("com.h2database:h2") 한 줄만 지운다. 본문이 빈 contextLoads 테스트는 어떻게 되는가?

    이 테스트의 검증은 본문이 아니고 @SpringBootTest에 있다. 컨텍스트는 Hibernate와 H2의 연결까지 띄운다. 설정 파일에 DB의 주소가 없으므로, H2가 classpath에서 사라지면 DB를 만들 방법이 없다. 포트를 열지 않는 것은 웹 서버의 이야기이고, DB와는 관계가 없다.

    다시 읽기: 스텝 3

  4. ADR-0003은 Spring Security를 쓰기로 이미 승인했다. 그런데 이 커밋에는 Spring Security가 없다. 가장 큰 이유는 무엇인가?

    이 커밋의 원칙은 "아직 쓰지 않는 것은 넣지 않는다"다. plan의 작업 1은 "빌드가 성공한다"와 "빈 애플리케이션이 뜬다"만 요구한다. 의존성을 그것을 쓰는 코드와 같은 커밋에 넣으면, 역사가 이유를 설명한다. Spring Security가 있어도 애플리케이션은 뜬다.

    다시 읽기: 핵심 아이디어

  5. spring.jpa.open-in-view의 기본값(켜짐)이 이 프로젝트의 헥사고날 구조에 해로운 이유는 무엇인가?

    켜져 있으면 영속성 컨텍스트가 HTTP 요청이 끝날 때까지 열려 있다. 그래서 웹 어댑터에서 도메인 엔티티를 직접 만져도 동작한다. ADR-0005는 "응답용 객체로 만든다"고 정했다. 끄면 그 실수가 바로 오류로 드러난다. ArchUnit은 패키지의 의존만 보므로 이 설정을 잡지 못한다.
