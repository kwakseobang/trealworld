commit f1b3cd4 (root commit, main)3 files+246 / −0
독자 가정: 이 문서를 같이 쓴 사람입니다. 프로젝트의 목적과 대화의 내용은 이미 압니다. 그래서 배경은 짧게 쓰고, 접어 두었습니다. 중심은 "이 커밋이 process로서 무엇을 보여주는가"와 "어디가 약한가"입니다. 세미나 청중에게 보여줄 때는 접힌 배경을 펴서 읽으면 됩니다.

1. 먼저 알아야 할 것

이 커밋은 저장소의 첫 커밋입니다. 그래서 "이전 상태"는 빈 폴더입니다. 모든 줄이 추가(+)입니다. 삭제는 없습니다.

그러나 "이전"이 정말 없는 것은 아닙니다. 비교할 기준은 저장소 밖에 있습니다. 일반적인 시작 방법이 그 기준입니다.

  • 일반적인 방법: API 스펙을 받는다. 엔드포인트를 하나씩 구현한다. 테스트가 통과하면 끝낸다.
  • 이 프로젝트의 방법: API 스펙을 "결과물"로 본다. 그 뒤에 있는 의도를 먼저 복원한다. 문서를 만든 뒤에 개발한다.
RealWorld가 무엇인가

RealWorld는 "Medium 같은 소셜 블로그"의 공통 스펙입니다. 여러 프레임워크가 같은 스펙을 구현해서 서로 비교합니다. 원본 저장소에는 구현이 없습니다. 계약만 있습니다.

  • specs/api/openapi.yml — 926줄. 엔드포인트 19개. 데이터의 모양을 정의합니다.
  • specs/api/hurl/ — Hurl 테스트 파일 13개. 그중 5개는 에러 전용입니다. 동작을 정의합니다.
  • specs/e2e/ — Playwright 테스트. 프론트엔드의 기준입니다.

이 프로젝트는 원본을 따르지 않습니다. 아이디어의 출처로만 씁니다 (결정 6.6).

spec, domain, ADR, plan이 각각 무엇인가
  • spec — 우리가 다시 쓴 요구사항. "무엇을 만드는가."
  • domain — 도메인 모델과 용어집. "어떤 개념과 규칙이 있는가."
  • ADR (Architecture Decision Record) — 설계 결정 하나와 그 이유를 적은 짧은 문서. "왜 이렇게 만드는가."
  • plan — 구현 계획. "어떤 순서로 만드는가."

이 커밋에는 넷 중 하나도 없습니다. 이 커밋은 그 앞 단계인 브레인스토밍입니다.

RFC 2119 키워드 (MUST, MAY)

요구사항의 강도를 정해진 단어로 표시하는 규칙입니다. CLAUDE.md가 이 규칙을 씁니다.

  • MUST = "반드시 ~해야 한다". 예외가 없습니다.
  • MAY = "~할 수 있다". 선택입니다.

문제는 이것입니다. 의도에서 출발하려면 코드를 쓰기 전에 정해야 할 것이 많습니다. 목적, 범위, 호환, 스택, 기록 방식. 이 커밋은 그것들을 정한 기록입니다.

2. 한 장의 그림으로 보는 생각

코드를 쓰기 전에, 모르는 것을 질문으로 꺼내고, 그 질문을 하나씩 결정으로 바꾼다. 그리고 바꾼 과정을 따로 남긴다.

이 커밋의 파일 3개는 역할이 서로 다릅니다. 킥오프 문서는 결론을 담습니다. 일지는 과정을 담습니다. CLAUDE.md는 규칙을 담습니다. 같은 사건이 세 곳에 서로 다른 형태로 들어갑니다. 예를 들면 "별도 일지를 쓴다"는 결정은 킥오프 문서에서는 결정 6.2이고, 일지에서는 스텝 5이고, CLAUDE.md에서는 MUST 규칙입니다. 이 세 겹의 구조를 알면 나머지 diff는 쉽게 읽힙니다.

이 커밋에 인터랙티브 위젯은 없습니다. 변경이 문서뿐이고, 입력을 바꾸면 출력이 달라지는 계산이 없기 때문입니다.

3. 변경을 단계별로 읽기

파일 순서가 아니라 생각의 순서로 읽습니다. 단계는 6개입니다.

단계 1 — 방법을 선언하고 입력 자료의 지도를 그린다

왜 이 단계인가: 의도를 추출하려면 먼저 "무엇에서 추출하는가"를 알아야 합니다. 그래서 첫 일은 원본 저장소를 읽는 것이었습니다.

docs/brainstorming/00-kickoff.md — 브레인스토밍의 결론을 모으는 문서입니다. 1절과 2절이 여기에 해당합니다.

## 1. 내가 이해한 의도API 스펙을 그대로 구현하지 않는다.스펙을 "결과물"로 보고, 그 뒤에 있는 **개발 의도**를 먼저 복원한다.… 9줄 생략 (파이프라인 그림) …진행 방식: 한 번에 하나만 한다. 각 단계는 대화로 확인한 뒤에 다음으로 간다.## 2. 입력 자료에서 본 것| 자료 | 위치 | 성격 ||---|---|---|| OpenAPI | `specs/api/openapi.yml` (926줄) | **무엇**을 주고받는지 || Hurl 테스트 | `specs/api/hurl/` | **어떻게 동작해야** 하는지 (정답 기준) |… 4줄 생략 (E2E, 문서 사이트) …엔드포인트는 19개다. 묶으면 6개 주제가 된다.

볼 곳은 표의 세 번째 열입니다. 자료마다 "성격"을 붙였습니다. OpenAPI는 모양이고 Hurl 테스트는 동작입니다. 이 구분이 뒤에 나오는 아이디어 A의 근거가 됩니다.

표시한 첫 줄이 방법 전체를 한 문장으로 말합니다. 스펙을 입력이 아니라 "누군가의 결과물"로 봅니다.

자료가 무엇인지 알았습니다. 다음은 거기에서 무엇을 읽었는지입니다.

단계 2 — 읽은 것은 가설로, 읽지 못한 것은 빈칸으로 나눈다

왜 이 단계인가: 스펙에서 읽은 의도는 추측입니다. 사실처럼 쓰면 나중에 틀린 것을 찾기 어렵습니다. 그래서 "추측"과 "스펙에 없는 것"을 두 절로 나눴습니다.

docs/brainstorming/00-kickoff.md — 3절(가설 7개)과 4절(빈칸 5개)입니다.

## 3. 스펙에서 읽히는 의도 (가설)아직 검증하지 않은 추측이다. 다음 단계에서 하나씩 확인한다.… 1줄 생략 (가설 1) …2. **읽기는 열려 있고, 쓰기는 닫혀 있다.** 글/프로필/태그 조회는 로그인 없이 된다. 변경은 모두 인증이 필요하다.3. **"나"의 관점이 응답에 섞인다.** `following`, `favorited` 는 같은 자원이라도 보는 사람에 따라 값이 다르다. 조회 모델이 "누가 보는가"에 의존한다.… 4줄 생략 (가설 4~7) …## 4. 스펙이 말해주지 않는 것 (빈칸)API 스펙은 "모양"만 말한다. 아래는 우리가 결정해야 한다.… 6줄 생략 (빈칸 5개) …이 빈칸들이 나중에 **ADR 후보**가 된다.

두 개의 표시한 줄이 이 단계의 핵심입니다. 첫 줄은 3절 전체에 "검증 전"이라는 딱지를 붙입니다. 둘째 줄은 빈칸을 다음 단계(ADR)의 입력으로 연결합니다. 지금 답하지 않고, 어디에서 답할지만 정했습니다.

가설 2는 주의해서 보십시오. 5절의 검토 노트에서 다시 다룹니다. 이 가설에는 반례가 있습니다.

무엇을 아는지와 모르는지가 나뉘었습니다. 다음은 "어떻게 진행할 것인가"에 대한 아이디어입니다.

단계 3 — 방법에 대한 아이디어를 내고, 틀린 것은 지우지 않고 긋는다

왜 이 단계인가: 가설은 "제품"에 대한 것입니다. 아이디어는 "작업 방법"에 대한 것입니다. 발표의 주제는 방법이므로, 이 절이 세미나에 가장 가깝습니다.

docs/brainstorming/00-kickoff.md — 5절(아이디어 A~F)입니다.

- **A. 의도는 OpenAPI보다 테스트에 더 많다.** Hurl 테스트는 엣지 케이스와 에러 규칙을 담고 있다. 의도 추출의 1차 자료로 Hurl 을 쓰는 것을 권장한다.- **B. 엔드포인트 단위가 아니라 "사용자 목표" 단위로 추출한다.** 예: "POST /articles" 대신 "작가가 글을 발행한다". 이렇게 하면 spec 이 API 모양에 묶이지 않는다.- **C. 의도마다 근거를 붙인다.** 각 의도에 "스펙의 어느 부분에서 읽었는가"를 적는다. 추측과 사실을 구분한다.- ~~**D. 원본 스펙은 마지막에 검증 도구로 다시 쓴다.** 개발이 끝나면 Hurl 테스트를 돌린다. 우리가 추출한 의도가 맞았는지 확인하는 수용 테스트가 된다.~~ → 6.6의 결정으로 폐기… 2줄 생략 (아이디어 E, F) …

표시한 줄을 보십시오. 아이디어 D는 커밋 시점에 이미 폐기된 상태입니다. 그런데 지우지 않았습니다. 취소선과 폐기 이유의 위치(6.6)를 남겼습니다.

이것은 이 저장소의 관례가 됩니다. 버린 것은 지우지 않고 긋는다. 7절의 열린 질문 목록도 같은 방식입니다. git 기록에는 D가 살아 있던 버전이 없습니다. 첫 커밋 전에 폐기됐기 때문입니다. 그래서 문서 안의 취소선이 유일한 흔적입니다.

아이디어 D가 왜 폐기됐는지는 다음 단계에 있습니다. 질문 하나의 답이 원인입니다.

일지에만 있는 항목은 두 가지입니다. 버린 대안과 관찰입니다. 관찰의 대부분은 AI의 잘못된 가정과 그 교정입니다. 성공만 있는 기록이 아닙니다.

일지는 이 대화에서는 계속 쓰입니다. 그러나 다음 세션의 AI는 이 대화를 모릅니다. 그 문제를 마지막 파일이 풉니다.

단계 6 — 합의한 것을 다음 세션이 읽을 규칙으로 고정한다

왜 이 단계인가: Claude Code는 세션을 시작할 때 프로젝트의 CLAUDE.md를 읽습니다. 여기에 없는 합의는 다음 세션에서 사라집니다.

CLAUDE.md — AI에게 주는 프로젝트 지침입니다. 19줄 전체가 이 커밋에서 추가됐습니다.

# CLAUDE.md## 프로젝트의 목적- 이 프로젝트는 방법론 실험이다. "API spec → 의도 추출 → spec → domain → ADR → plan → 개발" 흐름을 검증한다.- 과정을 세미나에서 사례로 발표한다. 예제(RealWorld)보다 **process**가 중요하다.- 작업은 베이비 스텝으로 한다. 한 번에 한 단계만 하고, 사용자와 확인한 뒤에 다음으로 간다.## 작업 일지- 스텝이 끝날 때마다 `docs/journal/YYYY-MM-DD.md`에 **반드시 기록해야 한다.** (MUST)- 스텝마다 쓰는 항목: 요청 또는 질문, 답, 한 일, 결정, 버린 대안, 관찰. 해당 없는 항목은 뺀다.- 프로젝트 문서에는 결론만 쓴다. 과정(왜, 어떤 순서로, 무엇을 버렸는가)은 일지에 쓴다.## 문서 언어- 이 프로젝트의 모든 문서는 **반드시 한국어로 작성해야 한다.** (MUST)- 대상: `docs/` 아래의 모든 문서(brainstorming, spec, domain, adr, plan)와 이 파일.- 코드 식별자, 파일 경로, API 필드 이름, 기술 용어는 원문(영어) 그대로 쓸 수 있다. (MAY)

세 절 중 사용자가 직접 요청한 것은 문서 언어 하나입니다. 프로젝트의 목적과 작업 일지는 AI가 요청 없이 넣었습니다. 일지의 스텝 6이 이 사실을 "AI가 앞서갔다"로 기록합니다.

MUST가 두 개 있습니다. 일지 기록과 한국어 작성입니다. MAY는 하나입니다. 영어 식별자의 허용입니다. 이 MAY도 AI가 제안한 것입니다.

이것으로 세 겹이 완성됩니다. 결론(킥오프 문서), 과정(일지), 규칙(CLAUDE.md). 다음 커밋부터는 이 구조 위에 spec, domain, ADR, plan이 쌓입니다.

5. 검토 노트

문서에는 실행할 코드가 없습니다. 그래서 "경계 입력"을 넣는 대신, 문서끼리 서로 맞는지와 원본 스펙과 맞는지를 확인했습니다.

  • 확인됨 가설 2에 반례가 있습니다. 그 반례가 첫 슬라이스 안에 있습니다. 가설 2는 "변경은 모두 인증이 필요하다"입니다. 원본 openapi.yml에서 POST /users(가입)와 POST /users/login(로그인)에는 security 항목이 없습니다. 가입은 회원을 만드는 변경입니다. 결과: 가설 2를 그대로 spec으로 옮기면 "가입에도 토큰이 필요하다"는 틀린 규칙이 됩니다. 의도 추출 단계에서 "인증을 얻는 동작은 예외다"로 고쳐야 합니다.
  • 확인됨 결정 6.3과 6.8이 같은 문서에서 서로 반대로 말합니다. 6.3: "어떤 슬라이스를 고를지는 아직 정하지 않았다." 6.8: "가입 → 로그인 → 회원 정보 조회." 결과: 6.3만 읽은 사람은 슬라이스가 미정이라고 생각합니다. 6.3의 둘째 줄을 "→ 6.8에서 결정"으로 바꾸면 됩니다.
  • 확인됨 "열린 질문은 모두 닫혔다"가 새로 열린 질문 2개를 가립니다. 6.6은 "검증 방법은 나중에 다시 정한다"라고 하고, 6.7은 "어떤 규칙인지는 아직 정하지 않았다"(ArchUnit)라고 합니다. 둘 다 7절의 목록에 없습니다. 결과: 7절만 보면 남은 질문이 0개입니다. 실제는 2개 이상입니다. 다음 세션이 이 둘을 놓칠 수 있습니다.
  • 확인됨 CLAUDE.md의 MUST 규칙이 커밋 직후에 이미 지켜지지 않았습니다. 규칙: "스텝이 끝날 때마다 반드시 기록해야 한다." 그런데 git init/커밋과 GitHub push 두 스텝은 일지에 없습니다. AI는 "결정이 없는 단순 작업"이라는 이유로 뺐습니다. 결과: 규칙과 실제가 다릅니다. 규칙을 "결정이 있는 스텝"으로 좁히거나, 모든 스텝을 기록해야 합니다. 어느 쪽인지는 작성자가 정할 일입니다.
  • 확인됨 문서 목록 두 곳에 journal이 없습니다. CLAUDE.md의 문서 언어 대상은 "(brainstorming, spec, domain, adr, plan)"입니다. 킥오프 문서의 아이디어 E도 같은 5개 폴더만 나열합니다. 둘 다 일지를 정하기 전에 쓴 것입니다. 결과: "docs/ 아래의 모든 문서"라는 말이 있으므로 일지도 한국어 규칙에 들어갑니다. 실제 문제는 작습니다. 그러나 목록만 보면 일지가 프로젝트 문서가 아닌 것처럼 읽힙니다.
  • 확인됨 입력 자료의 위치가 작성자의 컴퓨터 경로입니다. 킥오프 문서 5행: /Users/tobylee/workspace/sandbox/realworld. 원본 저장소의 URL이나 커밋 번호가 없습니다. 결과: 세미나 청중은 같은 입력을 찾을 수 없습니다. 원본이 바뀌면 "926줄, 19개"라는 숫자도 맞지 않게 됩니다. 재현하려면 원본의 URL과 커밋 번호가 필요합니다.
  • 추측 "Spring Boot 최신 버전"은 읽는 날짜에 따라 뜻이 달라집니다. 6.7에는 버전 번호가 없습니다. Java는 25로 고정됐습니다. 결과: 몇 달 뒤에 이 문서를 읽으면 "최신"이 다른 버전입니다. plan이나 ADR 단계에서 실제 번호로 고정하면 해결됩니다. 지금 단계에서는 의도한 것일 수 있습니다.
  • 추측 가설 7개 중 첫 슬라이스가 검증할 수 있는 것은 적습니다. 가설 3(following, favorited), 5(피드), 6(slug), 7(태그)은 글과 프로필에 대한 것입니다. 첫 슬라이스는 회원만 다룹니다. 결과: 슬라이스가 끝나도 이 가설들은 "검증 전"으로 남습니다. 둘째 슬라이스를 고를 때 이 점을 기준으로 쓸 수 있습니다.
