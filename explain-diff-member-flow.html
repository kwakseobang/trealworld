읽는 사람: Spring과 Spring Security를 잘 아는 개발자. 이 프로젝트의 문서(Spec 01, ADR-0003, ADR-0004)를 승인한 사람. 그래서 JWT와 @SpringBootTest의 기본은 설명하지 않는다. "이 테스트가 왜 필요한가"와 "무엇을 찾았는가"에 집중한다.

1. 먼저 알아야 하는 것

이 커밋은 메인 코드를 바꾸지 않는다. 테스트 클래스 1개와 일지를 더한다. 테스트의 수는 212개에서 213개가 된다.

작업 4, 5, 6은 가입, 로그인, 조회를 하나씩 만들었다. 기능마다 수용 테스트 클래스가 있다. 클래스마다 서버를 띄우는 설정이 다르다.

수용 테스트 클래스서명 키(trealworld.jwt.secret)조회에 쓰는 토큰
GetMemberAcceptanceTests고정 (TestTokens.SECRET)로그인이 준 토큰, 그리고 테스트가 직접 만든 토큰
ErrorResponseAcceptanceTests고정테스트가 직접 만든 토큰
FilterErrorAcceptanceTests고정테스트가 직접 만든 토큰
MemberFlowAcceptanceTests (새 클래스)정하지 않는다로그인이 준 토큰

나머지 2개(RegisterMemberAcceptanceTests, LoginAcceptanceTests)는 키를 정하지 않는다. 하지만 토큰으로 조회하지 않는다.

조회의 테스트가 키를 고정한 이유는 좋다. 만료된 토큰과 위조한 토큰을 테스트가 직접 만들어야 한다. 그러려면 테스트가 키를 알아야 한다.

키를 정하지 않으면 서버는 무엇을 하는가 (ADR-0003)

JwtSigningKey는 설정 trealworld.jwt.secret이 비어 있으면 시작할 때 임의의 32바이트 키를 만든다. 경고를 남긴다. 토큰을 발급하는 쪽(JwtAccessTokenIssuer)과 검사하는 쪽(디코더)은 이 bean 1개를 함께 쓴다. bootRun으로 띄운 서버가 이 상태다.

문제. "키를 정하지 않은 서버에서, 로그인이 준 토큰으로 조회한다"를 본 테스트가 없었다. 그것이 기본 설정이다.

2. 핵심 생각

부품의 테스트는 부품마다 편한 설정을 고른다. 흐름의 테스트는 실제와 같은 설정에서, 앞의 응답을 뒤의 요청에 그대로 넣는다.

새 테스트는 값을 직접 만들지 않는다. 가입한 회원으로 로그인한다. 로그인이 준 토큰으로 조회한다. 조회가 준 이름이 가입한 이름인지 본다. 서명 키는 정하지 않는다. 그래서 "서버가 스스로 만든 키로 발급한 토큰을 같은 서버가 받아들인다"가 처음으로 테스트의 안에 들어온다.

4. 바뀐 것, 순서대로

3번(직접 해 보기)은 없다. 이 커밋은 계산을 바꾸지 않는다. 움직여 볼 값이 없다.

단계 1 — 기본 설정으로 서버를 띄운다

이 단계가 이 커밋의 값의 대부분이다. 없는 것(properties = ...)이 중요하다.

src/test/java/trealworld/acceptance/MemberFlowAcceptanceTests.java — 새 파일. 수용 테스트의 7번째 파일이다 (도우미 TestTokens 포함).

단계 2 — 요청 4개를 앞의 응답으로 잇는다

테스트의 이름은 지나가는 수용 기준 3개의 ID로 시작한다. ADR-0004가 이름에 ID를 요구한다. 작업 7에는 자기의 ID가 없다.

    @Test    void ac1_1_ac2_1_ac3_1_a_visitor_registers_logs_in_and_reads_their_own_information() {        // 가입의 전에는 로그인할 수 없다. 뒤의 로그인의 성공은 가입의 결과다.        login().expectStatus().isUnauthorized();        // 목표 1. 방문자가 회원이 된다.        assertThat(mapOf(register().expectStatus().isCreated()))                .containsOnlyKeys("username", "email")                .containsEntry("username", username)                .containsEntry("email", email);        // 목표 2. 회원이 액세스 토큰을 받는다. 볼 곳 3개.

  • 첫 줄의 401. 가입의 전에는 로그인이 안 된다. 그래서 뒤의 200은 가입의 결과다. 이 줄이 없으면 "누구나 로그인된다"는 결함에서도 테스트가 통과한다.
  • containsOnlyKeys. 응답에 비밀번호의 해시나 id가 섞이면 실패한다.
  • 마지막 단언. 조회의 응답을 가입에 쓴 username, email과 비교한다. "어떤 회원이 나온다"가 아니라 "가입한 그 회원이 나온다"를 본다.

남은 것은 요청을 보내는 작은 메서드들이다.

테스트는 처음부터 통과했다. 구현이 이미 있었다. 그래서 "이 테스트가 무엇을 잡는가"를 따로 확인해야 했다. 6번이 그 결과다.

6. 리뷰 메모

새 테스트가 처음부터 통과했다. 그래서 메인 코드에 결함을 1개씩 넣고 전체 213개를 돌렸다. 결함은 커밋하지 않았다.

넣은 결함실패한 테스트새 테스트
D1. 발급과 검사가 서로 다른 임의의 키를 쓴다 (키를 정하지 않았을 때만)1개실패 — 이 테스트만
D2. 토큰의 sub에 다른 회원의 id를 넣는다19개실패
D3. 가입이 다른 비밀번호의 해시를 저장한다32개실패
D4. 조회가 앞의 회원을 돌려준다5개실패
  • 확인됨 · 고치지 않음 — 키를 고정하고 서버를 다시 시작하면 옛 토큰이 다른 회원의 정보를 읽는다. 입력: jake가 가입(id 1)하고 토큰을 받는다 → 같은 키로 서버를 다시 시작한다 → finn이 가입(id 1)한다 → jake의 토큰으로 조회한다. 결과: 200과 finn의 정보. AC-3.4를 어긴다. 원인: sub는 DB가 만든 번호다. 인메모리 DB는 1부터 다시 센다. 키를 정하지 않으면 일어나지 않는다 (옛 토큰은 401). 이 커밋의 범위가 아니다.
  • 확인됨 — 기본 설정에서 "로그인의 토큰으로 조회한다"를 보는 테스트는 이 1개뿐이다. 이 테스트를 지우면 D1을 잡는 것이 없다.
  • 읽음 — 실패의 글이 단계를 말하지 않는다. 글은 "200을 기대했는데 401이다"다. 로그인의 401인지 조회의 401인지는 줄 번호로만 안다.
  • 동작은 확인됨, 규칙은 추정 — bearer(소문자)와 토큰의 뒤의 공백을 서버가 받아들인다. 테스트가 없다. HTTP의 규칙으로 맞다고 기억한다. 확인하지 않았다.
  • 지키지 못한 것 — ADR-0004의 "테스트가 먼저 실패한다". 구현이 먼저 있었다. 빨강은 위의 표의 결함으로 봤다.

점수를 매기려는 것이 아니다. 아직 이해하지 못한 곳을 보여 준다. 권하는 규칙: 모두 맞히기 전에는 이 변경의 리뷰를 요청하지 않는다.

  1. 이 테스트를 GetMemberAcceptanceTests의 안으로 옮기면 무엇이 달라지는가?

    그 클래스는 trealworld.jwt.secret을 고정한다. 요청은 같아도 서버의 설정이 다르다. D1은 키를 정하지 않았을 때만 나타난다. 이름은 임의의 8글자가 있어서 겹치지 않는다.

    다시 읽기: 1. 먼저 알아야 하는 것

  2. 테스트의 첫 줄(login().expectStatus().isUnauthorized())을 지웠다. 어떤 결함을 놓치게 되는가?

    첫 줄은 "뒤의 로그인의 성공이 가입의 결과다"를 보인다. D3과 D1은 뒤의 줄(로그인의 200, 조회의 200)이 잡는다.

    다시 읽기: 단계 2

  3. D1에서 기존의 212개가 모두 통과한 이유는 무엇인가?

    GetMemberAcceptanceTests도 로그인의 토큰으로 조회한다. 하지만 키를 고정한다. 키가 설정에서 오면 발급과 검사가 같은 값을 읽는다. 수용 테스트는 mock을 쓰지 않는다.

    다시 읽기: 6. 결함의 표

  4. 리뷰 메모 1의 순서를 키를 정하지 않은 서버에서 그대로 한다. jake의 옛 토큰으로 조회하면?

    임의의 키는 서버를 다시 시작하면 바뀐다. 옛 토큰은 서명의 검사에서 떨어진다. 토큰에는 sub와 exp만 있다. 이름은 없다. 그래서 ADR-0003은 "DB가 인메모리인 동안" 임의의 키를 받아들였다.

    다시 읽기: 리뷰 메모 1

  5. 마지막 단언에서 containsEntry("username", username)을 빼고 containsOnlyKeys만 남겼다. D1 ~ D4 중 이 테스트가 더는 잡지 못하는 것은?

    D1은 조회의 401로, D3은 로그인의 401로 나타난다. 상태의 단언이 잡는다. D4는 200과 올바른 모양의 본문을 준다. 값을 비교해야 잡는다.
