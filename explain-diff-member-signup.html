1. 먼저 알아야 할 것

지금 어디인가

plan 01의 작업 4다. Spec 01의 목표 1(가입)을 만든다. 처음으로 HTTP 요청이 DB까지 간다.

이 커밋의 전

  • domain에 타입 4개가 있었다: Member, Email, Username, PasswordHash. JPA는 없었다.
  • application과 adapter는 비어 있었다. 엔드포인트가 없었다.
  • 아키텍처 테스트의 규칙 2, 4, 5는 검사할 클래스가 없어서 allowEmptyShould(true)로 통과했다.

코드의 모양을 정하는 규칙 3개

이 커밋의 패키지 구조는 ADR-0002의 규칙에서 나온다. 코드를 읽기 전에 이 3개를 기억한다.

  • 규칙 2: application은 adapter를 모른다. 그래서 DB와 BCrypt는 인터페이스(나가는 포트)의 뒤에 있다.
  • 규칙 4: adapter끼리는 서로 모른다. 웹은 영속성을 모른다.
  • 규칙 5: 웹 어댑터는 application.port.in만 쓴다. 유스케이스의 구현 클래스를 모른다.
record를 JPA의 @Embeddable로 쓰기

Hibernate 6.2부터 record를 @Embeddable로 쓸 수 있다. DB에서 읽을 때 record의 생성자를 부른다. 그래서 값 객체의 검사가 읽을 때도 실행된다.

이 프로젝트의 값 객체 3개는 필드의 이름이 모두 value다. 한 엔티티에 3개를 넣으면 열의 이름이 겹친다. @AttributeOverride로 열의 이름을 바꾼다.

Problem Details와 ResponseEntityExceptionHandler

RFC 9457은 오류의 본문의 모양을 정한다: status, title, detail, instance. 필드를 더할 수 있다. 미디어 타입은 application/problem+json이다. Spring의 ProblemDetail이 이 모양이다.

ResponseEntityExceptionHandler를 상속하면, Spring MVC가 던지는 오류(JSON이 아닌 본문, 틀린 메서드 등)도 같은 모양이 된다.

풀어야 할 문제: 가입의 규칙(R4, R6, R7)은 domain과 application에 둔다. HTTP, DB, BCrypt는 adapter에 둔다. 이 둘을 어떻게 이으면 규칙 2, 4, 5를 어기지 않는가?

2. 핵심 아이디어

규칙은 안쪽에 있고 기술은 바깥쪽에 있다. 둘은 인터페이스로만 만난다. 화살표는 모두 안쪽을 향한다.

  • 웹 어댑터는 요청을 받아서 들어오는 포트(RegisterMemberUseCase)를 부른다. 누가 구현했는지 모른다.
  • 유스케이스(RegisterMemberService)가 가입의 순서를 안다: 값을 검사한다 → 중복을 확인한다 → 해시를 만든다 → 저장한다.
  • 값의 검사는 domain의 값 객체가 한다. 유스케이스는 값 객체를 만들 뿐이다.
  • "저장한다"와 "해시를 만든다"는 나가는 포트다. 유스케이스가 인터페이스를 정하고, 어댑터가 구현한다.

이 그림에서 코드의 대부분을 예측할 수 있다. 상자 하나가 파일 하나다. 그림에 없는 것은 2개다: 예외 2개(port.in에 있다)와 조립하는 설정(UseCaseConfig).

    6. 리뷰 메모
    
  
    표시: [확인]은 서버를 띄우고 요청을 보내서 본 것이다. [읽음]은 코드에서 읽은 것이다. [추정]은 아직 일어나지 않은 일이다.
    
  
      
    
    1. 같은 값으로 동시에 가입하면 500이 나온다. [확인] 같은 요청 12개를 동시에 보냈다. 201이 1개, 409가 2개, 500이 9개였다. 요청들이 모두 "이메일이 없다"는 답을 받고 저장한다. DB의 unique 제약이 막는다. 회원은 1명만 생긴다. R6은 지켜진다. 그러나 응답이 틀리다. 500의 본문은 Problem Details도 아니다 (Spring Boot의 기본 모양이다). 유스케이스에 트랜잭션이 없는 것은 원인이 아니다. 트랜잭션이 있어도 같다. 제약의 위반을 409로 바꾸는 코드가 없는 것이 원인이다.
      2. 
    
    2. 긴 값은 500이 나온다. [확인] 300자인 사용자 이름, 300자인 이메일. DB의 열이 varchar(255)다. 길이의 규칙이 domain에 없다. 작업 3의 리뷰 메모 2에서 추정한 것이다.
      3. 
    
    3. 보이지 않는 사용자 이름으로 가입된다. [확인] {"username":" ", …} → 201. 작업 3의 리뷰 메모 1이 이제 HTTP로 닿는다.
      4. 
    
    4. JSON의 숫자가 글자가 된다. [확인] {"username":123, …} → 201, 사용자 이름은 "123"이다. Jackson의 기본 동작이다. 좋은 쪽의 확인도 있다: 모르는 필드(id, passwordHash)를 보내도 무시한다. 요청으로 id나 해시를 정할 수 없다.
      5. 
    
    5. R1의 보장이 약해졌다. [읽음] Member의 필드가 final이 아니고, protected 기본 생성자가 있다. 같은 패키지나 하위 클래스에서 빈 회원을 만들 수 있다. 또 하나: Hibernate는 DB에서 읽을 때 값 객체의 생성자를 부른다. 나중에 규칙을 강화하면(예: 메모 3을 막으면), 옛 규칙으로 저장된 회원을 읽을 때 예외가 난다 [추정].
      6. 
    
    6. 도메인의 예외 메시지가 API의 일부가 됐다. [읽음] value()는 IllegalArgumentException의 메시지를 그대로 errors에 넣는다. 응답에 나간다. Email의 메시지를 고치면 API의 응답이 바뀐다. 또 하나: 값 객체의 생성자 안에서 다른 이유로 IllegalArgumentException이 나도 "값의 오류"(400)가 된다.
      7. 
    
    7. 수용 테스트가 DB의 이름을 안다. [읽음] storedPasswordHash()의 SQL에 테이블(member)과 열(password_hash)의 이름이 있다. 매핑을 바꾸면 테스트가 깨진다. 그리고 unique 제약을 확인하는 테스트는 없다. 사용자 이름의 대소문자 구분(R7, 가정 2)은 DB의 설정에 달려 있다. H2는 구분한다. 구분하지 않는 DB로 바꾸면 Jake의 가입은 메모 1과 같은 500이 된다 [추정].
      8. 
    
    8. AI가 승인된 문서 4개를 고쳤다. [확인] 가장 큰 것은 Domain 01이다. 모델에 값 객체가 하나 늘었다 (Password). R4의 "지키는 곳"이 바뀌었다. 이 결정들을 승인하는가?
      9. 
  
    

    


    
  
    7. 이해했는지 확인하기
