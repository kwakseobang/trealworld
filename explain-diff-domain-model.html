독자: Java, Spring, TDD를 잘 아는 사람. Domain 01과 ADR-0002는 이미 읽었다. record와 ArchUnit의 설명은 접어 두었다. 필요하면 펼친다.

1. 먼저 알아야 할 것

지금 어디인가

plan 01의 작업 3이다. 도메인의 규칙 10개 중 4개를 만든다. 나머지 6개는 "지키는 곳"이 다르다.

규칙내용지키는 곳이 커밋
R1회원에게는 사용자 이름, 이메일, 비밀번호 해시가 항상 있다회원있다
R2이메일은 올바른 형식이다. 소문자로 저장한다이메일있다
R3사용자 이름은 비어 있지 않다. 앞뒤 공백을 지운다사용자 이름있다
R4비밀번호는 8자 이상, 72바이트 이하다가입없다 (작업 4)
R5비밀번호의 원문은 저장하지 않는다. 회원은 해시만 가진다회원있다
R6~R10유일성, 로그인, 조회가입, 로그인, 조회없다 (작업 4~6)

이 커밋의 전

  • trealworld.domain 패키지에는 package-info.java 하나만 있었다. 클래스가 없었다.
  • 아키텍처 테스트의 규칙 1, 3은 domain의 클래스를 검사한다. 검사할 클래스가 없었다. 그래서 allowEmptyShould(true)를 붙여서 통과시켰다.
  • 그 초록은 아무것도 증명하지 않았다. 패키지 이름에 오타가 있어도 통과했다.

domain이 받는 제약

  • domain은 Spring을 쓰지 않는다 (ADR-0002 규칙 3).
  • domain은 application과 adapter를 모른다 (규칙 1).
  • 도메인의 테스트는 Spring 없이 돈다 (ADR-0004).
record의 compact constructor

record Email(String value)에서 public Email { … }는 인자 목록이 없는 생성자다. 본문은 필드에 값을 넣기 전에 실행된다. 본문에서 value = …로 인자를 바꾸면, 바뀐 값이 필드에 들어간다. 예외를 던지면 객체는 생기지 않는다.

record의 equals는 필드의 값을 비교한다. 그래서 생성자에서 값을 정리하면, 정리된 값으로 비교된다.

ArchUnit의 allowEmptyShould

ArchUnit은 규칙의 that()에 맞는 클래스가 하나도 없으면 테스트를 실패시킨다. "검사한 것이 없다"를 통과로 보지 않는다. allowEmptyShould(true)는 이 보호를 끈다.

풀어야 할 문제: 규칙 R1, R2, R3, R5를 어디에 두면 아무도 건너뛸 수 없는가?

2. 핵심 아이디어

규칙을 검사하는 코드를 따로 두지 않는다. 규칙을 어긴 값은 처음부터 만들 수 없게 한다.

  • String은 아무 글자나 담는다. Email은 생성자를 지나야만 생긴다.
  • 생성자가 형식을 검사하고 소문자로 바꾼다. 그래서 Email 타입의 값이 있으면 R2는 이미 지켜졌다. 다시 검사할 필요가 없다.
  • Member는 이 타입 3개만 받는다. Member에는 String 필드가 없다.
  • 비밀번호의 원문은 String이다. Member에는 그것을 둘 자리가 없다 (R5).

이 그림을 기억하면 코드의 대부분을 예측할 수 있다. 타입 4개, 생성자의 검사 4개, 그리고 그것의 테스트다.

알아챌 것 3개:

  • 같은 문자열이 타입에 따라 다른 값이 된다. Email은 소문자로 바꾼다. Username은 대소문자를 그대로 둔다.

  • PasswordHash는 비어 있지 않으면 무엇이든 받는다. "password123"도 받는다.

단계 1 — 이메일을 타입으로 만든다 (R2)

가장 규칙이 많은 값이다. 형식과 소문자, 두 가지를 한 곳에서 지킨다.

  • 마지막 테스트는 value()가 아니고 객체끼리 비교한다. AC-1.8과 AC-2.5의 기초다.

package trealworld.domain;import java.util.Locale;import java.util.regex.Pattern;/** * 이메일. 올바른 형식이고, 소문자로 저장한다. (R2) */public record Email(String value) {	private static final Pattern FORMAT = Pattern.compile("[^@\\s]+@[^@\\s]+\\.[^@\\s]+");	public Email {		if (value == null || !FORMAT.matcher(value).matches()) {			throw new IllegalArgumentException("이메일의 형식이 올바르지 않다");		}		value = value.toLowerCase(Locale.ROOT);	}}
  • 정규식의 뜻: @가 정확히 하나다. 공백이 없다. @의 뒤에 .이 있다. 그 이상은 보지 않는다.
  • matches()는 문자열 전체가 맞아야 참이다. ^와 $가 필요 없다.
  • 순서가 중요하다. 검사가 먼저이고 value = …가 나중이다. 바뀐 값이 필드에 들어간다.
  • Locale.ROOT: 서버의 로케일이 터키어이면 "I".toLowerCase()는 ı가 된다. 로케일을 고정해서 막는다.

이메일이 "검사 + 정리"의 본보기가 됐다. 사용자 이름은 같은 모양에 규칙만 다르다.

표시: [확인]은 실제 클래스를 실행해서 본 것이다. [읽음]은 코드에서 읽은 것이다. [추정]은 아직 일어나지 않은 일이다.

  1. 보이지 않는 사용자 이름이 통과한다. [확인] new Username(" ")(NBSP 하나)가 만들어진다. ​(폭이 없는 공백), ﻿도 같다. isBlank()가 이 글자들을 공백으로 보지 않는다. 결과: 화면에서 이름이 빈 회원이 생길 수 있다. R3 "비어 있지 않다"의 뜻을 정해야 한다.
  2. 이메일의 형식 검사가 느슨하다. [확인] a@b.c, jake@example..com, jake@exam　ple.com(전각 공백 포함)이 통과한다. 정규식의 \s는 ASCII의 공백만 본다. 길이의 제한도 없다. R2의 "올바른 형식"이 무엇인지는 문서에 없다. AI가 정했다.
  3. PasswordHash는 원문을 막지 못한다. [확인] new PasswordHash("password123")이 만들어진다. R5의 테스트는 Member의 필드의 타입만 본다. 원문을 PasswordHash에 싸서 넣으면 통과한다. Object나 다른 record로 감싼 필드도 통과한다 [읽음]. R5의 실제 보장은 작업 4의 해시 포트에서 생긴다.
  4. PasswordHash를 출력하면 해시가 보인다. [확인] toString()의 결과는 PasswordHash[value=$2a$10$abc]다. record의 기본 동작이다. 로그에 이 객체를 넣으면 해시가 로그에 남는다. Member에는 toString이 없어서 회원을 출력할 때는 나가지 않는다.
  5. 같은 값의 회원 2명이 서로 다르다. [확인] Member.register(…)를 같은 값으로 두 번 부르면 equals가 거짓이다. Member에 id와 equals가 없다. 지금은 문제가 없다. 작업 4에서 id를 넣을 때 정해야 한다.
  6. 예외의 타입이 정보를 싣지 않는다. [추정] 모든 위반이 IllegalArgumentException이다. AC-1.2는 "어느 값이 문제인지 알려준다"를 요구한다. 지금은 메시지의 글자에만 있다. 작업 4에서 웹 어댑터가 이 타입을 통째로 422로 바꾸면, 라이브러리가 던진 IllegalArgumentException도 422가 된다.
  7. "Spring 없이 돈다"를 지키는 테스트는 없다. [읽음] ArchitectureTests는 테스트 클래스를 읽지 않는다 (DO_NOT_INCLUDE_TESTS). domain의 테스트에 @SpringBootTest를 붙여도 잡히지 않는다. 지금은 실행 시간(30개에 0.05초)과 import가 증거다.

질문 하나: 이메일은 앞뒤 공백을 거부하고, 사용자 이름은 지운다. 복사해서 붙인 "jake@example.com "은 형식 오류가 된다. 의도한 차이인가? R2에 "지운다"가 없어서 이렇게 됐다.

7. 이해했는지 확인하기

점수를 매기는 시험이 아니다. 아직 이해하지 못한 곳을 찾는 도구다. 규칙 하나: 다 맞히기 전에는 이 변경의 리뷰를 요청하지 않는다.

  1. new Email("Jake@Example.COM").equals(new Email("jake@example.com"))의 결과와 이유는?

    compact constructor에서 바꾼 값이 필드에 들어간다. 두 객체의 필드는 모두 "jake@example.com"이다. Email에는 equals를 재정의한 코드가 없다. 규칙을 생성자 한 곳에 두면 비교도 함께 해결된다.

    다시 읽기: 단계 1

  2. 이 커밋에는 비밀번호의 길이(R4: 8자 이상, 72바이트 이하)를 검사하는 코드가 없다. 가장 맞는 이유는?

    Domain 01의 표에서 R4의 "지키는 곳"은 가입이다. Member와 PasswordHash는 원문을 본 적이 없다. PasswordHash의 생성자는 빈 값만 거부한다. 원문은 작업 4의 유스케이스에 처음 나타난다.

    다시 읽기: 1. 먼저 알아야 할 것

  3. Member에 private String nickname; 필드를 더했다. 비밀번호와 관계가 없는 필드다. 테스트는 어떻게 되는가?

    첫 R5 테스트는 CharSequence, char[], byte[] 타입의 필드를 모두 금지한다. 의도와 관계없이 "글자를 그대로 담는 자리"가 생기면 실패한다. 새 값을 더하려면 Username처럼 값 객체로 만들어야 한다. R1의 테스트는 필드의 개수를 세지 않는다.

    다시 읽기: 단계 4

  4. new Username(" ")을 실행한다. 인자는 NBSP(줄 바꿈 없는 공백) 한 글자다. 결과는?

    Java의 isBlank()와 strip()은 NBSP를 공백으로 보지 않는다. 검사도 통과하고, 지워지지도 않는다. 화면에서는 이름이 빈 회원으로 보인다. 전각 공백(　)은 반대로 거부된다. "비어 있지 않다"의 뜻이 코드의 공백 정의에 달려 있다.

    다시 읽기: 6. 리뷰 메모 (1번)

  5. 누군가 패키지 domain을 model로 바꿨다. ArchitectureTests의 상수는 고치지 않았다. 이 커밋의 뒤에 아키텍처 테스트는 어떻게 되는가?

    규칙 1, 3에서 allowEmptyShould(true)를 지웠다. 이제 "검사한 클래스가 없다"는 실패다. 규칙 2, 4, 5에는 아직 남아 있어서 통과한다. 지우기 전에는 5개가 모두 초록이었을 것이고, domain의 규칙은 아무것도 지키지 않게 됐을 것이다.

    다시 읽기: 단계 5
